## [fail:design] empty-collection-is-not-absent | 2026-08-05 | count:1
A feature that ACTIVATES on a filtered collection silently produces an EMPTY activation instead of no activation, and the empty form is truthy. Concretely: the second skill draft filters the card pool by "not already offered, not already held"; with a pool of exactly one offer's worth the filter empties, `pickDistinct` returned `[]`, and `offers = []` still gated board play while yielding zero `draft_pick` actions — a match with no result and no legal action, reachable from perfectly valid content. Fix was two-part and both parts matter: the producer refuses to open an offer it cannot fill (`drawn.length === DRAFT_OFFER_SIZE`), and the consumer treats an empty collection as absent (`(offers?.length ?? 0) > 0`, not `offers ?`). The guard that actually catches this class is a loop-invariant assertion over randomized play — "if the match has no result, it has at least one legal action" — not a scripted line, which never reaches the boundary. Generalization: whenever a filter feeds a fixed-size requirement, write down what happens when the filter empties, and assert the invariant rather than the happy path.
## [fail:design] shared-vocabulary-unshared-code-path | 2026-08-05 | count:2
One shared vocabulary, two code paths — and only one of them ran the pipeline. `apply` routed a board move through the E1..E7 lifecycle but sent a card play straight to E6/E7, so the SAME declarative action (`teleport_piece`) fired the destination square's `on_enter` when a square or piece owned it and silently skipped it when a card owned it. A warp became the only way to walk onto a hostile square unharmed, and nothing in the schema showed that — the two actions are literally the same word. The cost is not the bug, it is that no content author could ever have found it: the vocabulary promised sameness the interpreter did not keep. Fix: extract the cascade (`cascadeEnter`) and route both branches plus E5 promotion through it. The regression test that pins it asserts a board move and a card-driven move produce the SAME resolution log. Generalization: when a design claims "X means the same thing regardless of who owns it", write the test that drives X from each owner and compares, because a shared grammar over unshared code paths is the failure that hides best. `spawn_piece` still has this shape and is recorded as an open gap rather than quietly fixed.

## [fail:test] all-positive-fixture-hides-overcounting | 2026-08-05 | count:2
A fixture in which every instance is a positive cannot detect an implementation that ignores the predicate entirely. Concretely: a three-check win condition was tested with a move sequence where every one of the mover's moves genuinely delivered check, so an engine that incremented the counter on "the mover completed a ply" — never evaluating whether check was actually given — produced the identical counter sequence and passed the whole describe block including the win-on-third assertion. The reviewer caught it before implementation; had it landed, the bug would have shipped behind a green suite. Fix: insert a deliberate DUD into the sequence (a mover move that does not satisfy the predicate) and assert the counter is unchanged across it. Generalization: for any counter, filter, or guard, the load-bearing fixture is the negative instance interleaved with the positives — not more positives, and not a separate happy-path test. The same reasoning produced the paired control elsewhere in that file: assert the protected case AND the identical position with the protection removed, so the assertion is about the mechanism rather than about the position.

The reviewer predicted the storage shape from the frozenUntil precedent. Fix: hold the subject still and burn plies with a different piece, so the only variable is the clock.

## [fail:test] assertion-equals-its-own-default | 2026-08-05 | count:1
A test whose expected value equals the implementation's own default never exercises the thing it names, and reads as full coverage. This is distinct from a missing negative instance: the fixture has a positive, drives the right control, and still proves nothing, because the asserted state was already true before the control was touched. Four review rounds on one file found it in three disguises — a whole-draft subtree search that matched an editor default (`condition: always`, `target: self`, `destination: chosen_empty` are all defaults, so a dead button passed); a trigger axis where the fresh object was seeded with the very trigger under test, and for a single-valued host (`skillCard` admits only `on_play`) there was no other value to switch to at all; and a parameter whose default came from `firstPiece(ctx)`, so asserting `to: 'piece.king'` against a set whose first piece IS the king proved nothing. Per-row hand-written discriminators fixed each instance and would have rotted on the next row added. The fix that holds is structural and belongs in the RUNNER, not the rows: before touching the control, assert the target path does NOT already hold the expected value. Two things that guard does not cover, and both bit — it fires once, so a SECOND control applied afterwards (a parameter following the main click) stays unguarded, and it cannot see a write that is idempotent with an earlier step's. What settles it is mutation: kill the control's write and confirm the suite goes red. Before the fix, killing either of two controls left 203 tests green while every authored promotion silently targeted the set's first piece. Generalization: for any "this control writes X" test the load-bearing fact is the PRE-state, and picking an expected value the implementation cannot produce by accident is cheaper than arguing that it would not.
## [fail:design] rule-keyed-to-event-not-state | 2026-08-05 | count:1
A terminal condition attached to the EVENT that usually causes it, rather than to the STATE it produces, is silently skipped by every other route to that state. The match-ending rule "capturing the king wins" was implemented as a short-circuit inside the capture step of the pipeline, which was correct while capture was the only way a king could leave the board. It stopped being the only way the moment the effect vocabulary gained a destroy action with a chosen target — and a shipped card does exactly that. A king DESTROYED rather than captured left no result behind, so play continued for another fifty plies with king-capture victory unreachable for BOTH sides, and neither the type system nor six phases of scripted tests noticed, because no hand-written fixture had ever played the line where a card kills a king. It was found on the third generated seed of a random-play invariant walk. The fix is the generalization: judge the STATE ("this side has no royal") rather than the event, and judge it as a TRANSITION — had one at the start of the ply, has none at the end. Both halves matter; the first attempt judged against the board's starting definition and wrongly condemned a legitimately royal-less puzzle position, which is exactly what the editor's preview builds. Two rules follow. When a win/loss/termination condition is written, ask what OTHER mechanisms can reach the same state and key the rule to the state. And when a vocabulary gains an action that can remove, create or relocate a piece, re-audit every rule written when fewer mechanisms existed — a new action does not announce which old invariants it just widened.
## [fail:test] unasserted-fixture-premise | 2026-08-05 | count:1
A test states a premise about its own fixture and never checks it, so a green suite certifies an experiment nobody ran. Two instances landed in one phase, both caught by review before implementation. First: an acceptance criterion reading "1000 self-play matches played by a UNIFORM-RANDOM legal-action agent" was covered by a statistical suite that constrained the median and nothing else — an agent written as `legalActions[0]` is deterministic, terminates, and satisfies that whole file plus the determinism suite plus the invariant walk, while measuring the first-legal-move line instead of random play. The project's headline "a match is short" claim would then have rested on a degenerate fixture. Second: a bias test compared draft offers reached "down different lines" without ever asserting the lines differed, and the modular arithmetic generating them really could collapse two variants onto the same choices — in which case it compared a run to itself. Concretely, this phase added a test file for the agent (distribution flatness, no first/last index bias, reproducibility, null exactly when nothing is legal) and made the bias test return the position it arrived at so every comparison asserts the positions differ first — and count how many genuinely differing comparisons were made, so a fixture that silently stops varying fails instead of passing quietly.

A fix scoped to the evidence a critique happened to cite reproduces the very defect when the defect IS one of scope, and the second pass reads as progress because the first three files now check out. Concretely: a plan-validator flagged that a new PLAN's ADR-001..ADR-010 collided with ADR numbers already burned into the codebase, and named `schema.ts`, `Edit.tsx` and `Play.tsx` as its evidence. ## [fail:design] comment-claims-unbuilt-safeguard | 2026-08-06 | count:1
A comment that states a safeguard is more durable than the safeguard, so a design invariant written in prose and implemented in only one branch reads as satisfied everywhere and is trusted by the next reader. Concretely: a new design-token file opened with "the two sides are separated by hue AND by weight, not hue alone — roughly one in twelve boys reads red/green poorly", and neither half of that was true. No selector anywhere set a per-side `font-weight` — the weight cue existed only in the sentence claiming it. And the dark palette, authored in the same file below that sentence, gave the two sides `#93c5fd` and `#fca5a5`, whose relative luminances are 0.540 and 0.545 — indistinguishable in lightness, leaving exactly the hue-alone dependence the comment forbade, while the light palette a few lines earlier did carry a real lightness gap. Two independent reviewers found it; one read the comment against the stylesheet and called it documentation drift, the other computed the luminances and showed the invariant was actively violated in one theme. Fix was to implement rather than retract: a per-side font-weight in the component CSS, a dark side-colour with a real lightness gap that still clears 4.6:1 against the board, and a comment that now says where the weight half lives and that review found it claimed before it existed. Generalization: a comment asserting a PROPERTY (accessible, deterministic, thread-safe, idempotent) is a claim that needs a test, not documentation — and the specific shape to distrust is an invariant stated once at the top of a file whose body then branches, because the statement is written while looking at the first branch. The cheap guard is to write the property as an assertion in the same commit as the sentence; where that is genuinely hard, phrase the comment as intent ("should") rather than as fact ("is"), so the next reader knows to verify rather than rely.
## [fail:test] test-setup-hides-the-failure-path | 2026-08-06 | count:1
A test that grants, mocks, or stubs the very condition whose absence is the risk certifies the happy path and makes the dangerous branch permanently unreachable — and its greenness is read as "this is covered". Concretely: a copy-the-seed button was written as `void navigator.clipboard?.writeText(x); setCopied(true)`, reporting success unconditionally, so on an insecure context or an older mobile browser — where `navigator.clipboard` is undefined or the promise rejects — a child taps the button, reads the success label, and shares nothing. The e2e test written for that button opens with `context.grantPermissions(['clipboard-read', 'clipboard-write'])`, which guarantees the API is present and permitted, so the only branch it can ever exercise is the one that works. The reviewer found it by reading the code, not by running anything; no test could have. Fix: let the promise decide (`copied` / `failed` / `idle`), give failure its own visible label, and expose the state on an attribute so a test can assert it. Generalization: whenever a test's SETUP mentions the same capability the code under test is optional about — permissions granted, a network stubbed as available, an env var set, a feature flag forced on, a file created that production may not find — the absent case has no coverage by construction, and that is precisely the case where the code is most likely to lie. The cheap guard is to write the negative test first, or at minimum to name the missing branch in the test file so the gap is visible rather than implied. Related in shape to [fail:design] built-but-not-wired: the artifact is honest about what it measures and silent about what nobody asked it.
## [fail:design] counter-as-proxy-for-a-state | 2026-08-06 | count:1
A counter that sits near the thing you mean is not the thing you mean, and substituting it produces a guard that is silent in exactly the state it exists to protect. Concretely: a confirm-before-discard gate was added to a hot-seat game after review found that a mis-tap on the always-visible new-match button destroyed a shared in-progress match with no way back. The gate asked `state.plyCount > 0` — "has anyone moved yet" — as its proxy for "is there a match worth keeping". But a draft pick does not advance the ply counter in this engine, so a match in which BOTH players had already chosen their skill cards reported nothing-to-lose and was discarded without a prompt: the single state where a mis-tap costs the most was the one state the guard ignored. The predicate that actually means what it says is `match.states.length > 1` — one applied action of any kind. Two things made this findable. The proxy was wrong in the safe direction for the tests that already existed (fresh mounts have neither plies nor actions, so nothing changed), and the ONLY reason it surfaced is that a test for the new guard was written immediately after the fix and failed against it. The fix had otherwise shipped with no coverage at all, which is the deeper error: a guard added without a test that exercises the guarded state is indistinguishable from no guard the moment the predicate drifts. Generalization: when a guard's condition is a counter, ask which state transitions increment it and list the ones that do not — the answer is the set of cases your guard is blind to. Prefer a predicate over the state you actually mean (was an action applied, does a document exist, is the buffer non-empty) over an adjacent metric that usually correlates.
