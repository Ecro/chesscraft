## [fail:test] distinct-is-not-distinguishable | 2026-08-06 | count:1
Asserting that two values DIFFER proves nothing about whether a person can tell them apart, and the gap between the two is where a whole feature can ship invisible. Concretely: a chessboard's checker pattern was added, with a test asserting the two square colours were not the same string. They were not: `#f2efe9` and `#ded5c4`, which is a contrast ratio of 1.27:1 — a board a child reads as flat. The feature was "added", the test was green, and the deliverable did not exist. The same project had already recorded the identical shape one file away: a painted-square gradient sitting at 1.03:1 against the plain square while its stylesheet comment declared it "distinguishable at a glance". Fix: assert a luminance step, not inequality — compute the WCAG ratio in the browser and give it a floor. What the numbers then forced is the second half of the lesson: a 3:1 checker drives the tinted glyphs standing on those squares below 3:1 themselves, so the two requirements trade on one axis and the honest output is a measured table plus a stated choice, not a silent pick. Generalization: for any property a HUMAN has to perceive — colour difference, animation duration, font size, audio level, latency — the assertion must carry a magnitude and a threshold. `a !== b`, `toBeTruthy()`, "the class is applied", "the element exists" are all statements about the code's intent, and intent is exactly what is never in doubt. Ask what the smallest version of this that a user could NOT perceive would look like, then check the test still fails on it.
## [fail:design] api-absent-on-the-target-platform | 2026-08-06 | count:1
An API that compiles, has types, and runs in the developer's browser can still be absent on the platform the product actually ships to, and nothing in the toolchain says so. Concretely: drag-to-move was built on HTML5 drag-and-drop — `draggable`, `dragstart`, `dragover`, `drop`. It type-checks, it is in every reference, and it works in a desktop browser. iOS Safari does not dispatch those events for a touch gesture on a generic element, and Android's support is inconsistent, so on the only platform this product targets — two children sharing one phone — a finger on a piece did nothing at all. The fix was pointer events, which cover mouse, touch and stylus through one path. Two independent reviewers found it, one by checking the API against the platform and one by asking what happens when a child touches the board; it was the second cross-reviewer convergence of the project, and both times the converged finding was the most severe of its round. Generalization: for any browser or runtime API, the question is not "does this exist" but "does this exist on the device in the user's hand", and the two answers differ most often for input (drag, hover, contextmenu, vibrate, clipboard), for media, and for storage. A quick check is whether the API predates the platform's dominant input method — HTML5 DnD was designed for a mouse in 1997 and touch was retrofitted around it, never into it. The companion failure is that the test suite said yes: see the occurrence note added to `test-setup-hides-the-failure-path` on the same day.
## [fail:render] fixed-overlay-blocks-what-it-only-dims | 2026-08-06 | count:2
A full-viewport fixed layer added to DIM the page also intercepts every pointer on it, and a fixed sheet covers the bottom of the viewport at every scroll position, so an overlay written as a visual effect quietly becomes a modal trap plus an unreachable page tail. Concretely: the card draft moved out of the document flow into a bottom sheet over a `position: fixed; inset: 0` scrim so it would stop pushing the board off the phone. The scrim was purely decorative in intent — it only sets a background — but it sat above everything, so the nav tabs, the home button and the whole tools row went behind glass the moment an offer appeared. The e2e suite reported it as twenty failures with `<div class="draft-scrim"> intercepts pointer events`, which made it look like a test-fixture problem; the player-facing version was worse than any test, because a child who opened a match and did not want to draft had no way out except reloading. If the intent is "dim", declare `pointer-events: none` in the same edit as the background, and give back `auto` only on the thing meant to be interactive. If the intent really is modal, that is a decision about whether the user can leave, so it needs an explicit way out, not merely an overlay. ## [fail:render] contrast-set-not-closed-over-cues | 2026-08-06 | count:2
A measured contrast suite proves only the pairs it enumerates, so a colour changed to satisfy one measured constraint can silently collapse a different cue that shares the same surface — and the suite stays green because that pair was never a row in it. Concretely: Phase 6a repainted the special squares green to clear a measured "painted vs plain >= 3:1" floor, and `e2e/contrast.spec.ts` verified exactly that, in both themes, with real luminance maths. What no row covered was `--color-legal` (also green) sitting on top of that new fill: ~1.4:1 light, ~1.37:1 dark. The single cue that tells a player "you may move here" all but disappeared on precisely the squares whose ability makes the decision hard, and the suite that exists to prevent this reported success. The companion defect is semantic rather than numeric: green conventionally means go/safe, so the most dangerous square on the board — destroy-anything-that-enters — was the one wearing the reassuring colour. Fix had two halves, and the second is the durable one: the fill moved to violet (no collision, no wrong connotation), AND the legal cue stopped depending on a single colour clearing every fill it can land on — it is now a dot inside a black/white ring whose two tones are theme-INVARIANT, so whatever the square is, one tone separates from it. Generalization: a contrast table is a set of PAIRS, and the set is only honest if it is closed over every pair of things that can occupy the same pixels — foreground cues over every background they can land on, not just background-vs-background. When you add a colour or move an existing one, the question is not "does it still clear its own row" but "which pairs does this colour now participate in that have no row". The cheap structural guard is to stop making a lone hue load-bearing: a cue sandwiched between two invariant extremes needs no row at all, because it cannot be washed out by a fill it does not touch.

## [fail:render] sticky-inert-under-overflow-ancestor | 2026-08-06 | count:1
`position: sticky` is silently inert when any ancestor has an `overflow` other than `visible`, and `overflow-x: hidden` is such an ancestor even though nothing about it looks vertical. CSS computes a used `overflow-y` of `auto` whenever the other axis is not `visible`, so a container written years earlier as `main { overflow-x: hidden }` — added to stop a wide element scrolling the page sideways — quietly becomes the scroll container that a later sticky element positions against. That container does not scroll internally (it has no height constraint; it grows), so the sticky never activates and there is no error, no warning, and nothing in the computed style that reads as wrong: `position` still says `sticky`. Concretely: a landscape layout put the board in a grid column and made it sticky so a tall neighbouring column could scroll past it. Measured after the change, scrolling a 790px document in a 412px window left the board at **-293px** — entirely off screen, exactly as before the fix. A second guess (`align-self: start`, on the theory that a row-spanning grid item fills its area and has nowhere to slide) changed nothing, because that was not the cause either. The fix was `overflow-x: clip`, which clips without establishing a scroll container; after it the same measurement put the board fully on screen with horizontal scroll still zero. Generalization: when a sticky element does not stick, walk every ancestor for `overflow` on EITHER axis before touching the element itself — `hidden`, `auto`, `scroll` and `clip` are not interchangeable here, and only `clip` preserves stickiness. The wider lesson is that `overflow-x: hidden` has a vertical side effect that its name denies, so it is worth writing down wherever it appears. And the meta-lesson: two plausible CSS explanations were tried and both were wrong; the thing that settled it was measuring the element's box after a real scroll in a real browser, which took less time than either guess.
## [fail:design] plan-contradicts-its-own-adr | 2026-08-06 | count:1
A PLAN can contradict itself, and when a phase's scope line and an ADR in the same document disagree, implementing the scope line is the natural mistake because that is the part being executed. Concretely: ADR-018 recorded "keep AC-017's model — both hands, one board, both trays always visible", and the scope of a later phase in the SAME plan listed "card-shaped collapsible trays". Those cannot both hold. The implementation followed the scope bullet, because that is what an execute stage reads, and shipped a collapse that unmounted the cards — so a tap on the opponent's label hid their hand in a game whose whole premise is that both hands are open, and a player who left their own tray shut could not play a card on their own turn, because the button they needed did not exist. Nothing caught it: the phase's own exit criterion asked only that collapsing not reflow the board, which the broken version satisfied perfectly. A reviewer found it by reading the ADR that sat three sections above the scope it contradicted. Fix was to make collapsing CONDENSE rather than hide — cards stay mounted, only their prose is hidden — which satisfies both the ADR's constraint and the gap the scope line was chasing, plus a test that asserts the card count survives a collapse. Generalization: a scope line is a task, an ADR is a constraint, and constraints outrank tasks. Before implementing a scope bullet that changes what a user can see or do, grep the plan's own ADR section for the nouns in that bullet — here, "tray" and "visible" would have found it in seconds. The tell is a scope item phrased as a UI affordance ("collapsible", "hidden by default", "behind a toggle") in a project whose ADRs constrain what information must remain available; those two vocabularies overlap and the document will not flag the collision itself.
## [fail:render] hidden-subtree-took-the-a11y-name | 2026-08-06 | count:1
`display: none` removes a subtree from the accessibility tree, so a control whose accessible name lives only inside that subtree becomes a nameless button the moment the subtree is hidden — and it announces as "button", which is worse than the state the hiding was meant to improve. Concretely: a card in a player's hand rendered as a button containing an icon span marked `aria-hidden="true"` and a body span holding the card's name and description. A collapse feature then hid the body with `display: none` to condense the tray. The visual result was fine — the icon still identified the card — but the accessible name computation was left with an explicitly-hidden icon and a removed subtree, so every card in a collapsed tray had no name at all for a screen reader. The e2e written for that same feature asserted the card count and that the first card was visible; neither says anything about a name, so the regression was invisible to a green suite. Fix was `aria-label` on the button itself, so the name survives whatever happens to the body, plus an assertion on that attribute. The two shapes to distrust are an `aria-hidden` icon paired with visible text (hide the text and nothing is left) and a visually-hidden label class swapped for `display: none` (which is not the same thing: `display: none` hides from AT, a clip-rect utility does not). The cheap guard is to put the name on the control rather than in its children, so that presentation changes cannot take identity with them.
## [fail:design] clearance-inherits-the-suites-blind-spot | 2026-08-06 | count:1
A reviewer that validates code against its test suite inherits every blind spot that suite has, and reports the inheritance as a clearance — which is worse than silence, because the next reader reads "checks out" as evidence rather than as a restatement. Concretely: `commitDraft` gained an optional `openedId` so a rename would replace a record instead of appending a duplicate. A code reviewer returned zero P0/P1 and wrote that "the `matchId` fallback, the stale-`openedId`-append path, and base immutability on both the accept and reject paths all check out against the seven cases in `tests/editor/rename.test.ts`." Every word of that was true. None of the seven cases had an id COLLISION, so the suite was structurally incapable of reaching the defect: when `openedId` named a record the document no longer had AND the author had typed an id already belonging to a different record, the fallback matched that other record and the save REPLACED it and validated — silent destruction of an unrelated record, reported to the author as success. A cross-model reviewer, given the same diff and no access to the first verdict, named it directly. The disagreement was settled by neither: the case was EXECUTED, and the probe printed `ok = true` with the victim's movement overwritten. Fix: `openedId` alone decides which record is replaced (`findIndex(r => idOf(r) === (openedId ?? id))`), so a stale id matches nothing, the record is pushed, and the loader refuses the document with `duplicate id`. Generalization: "I checked it against the tests" is a claim about the tests, not about the code, and it is strongest exactly where it is emptiest — a suite written by the same person who wrote the code shares that person's model of which cases exist. The cheap guard when a reviewer clears a specific path is to ask which test would FAIL if that path broke, and to name it; if the answer is a suite rather than a case, the clearance is unearned. Corollary observed the same round: when the re-review then cleared a second path "by inspection", writing that case took two minutes and converted the confidence into a measurement. It passed — which is a different fact from the one inspection offered.
## [fail:tooling] add-all-swallows-a-nested-checkout | 2026-08-06 | count:1
`git add -A` will happily stage a nested git checkout as a gitlink, producing a commit that looks complete and contains none of the nested content — and the workflows that create such checkouts do not gitignore them for you. Concretely: the `/hm:` stages create git worktrees under `.worktrees/`, which was absent from `.gitignore`. A stale `.worktrees/augmentchess-quality-parity/` from an earlier task therefore sat untracked, and the `git add -A` that every wrapup runs — itself the fix for an earlier failure where staging only indexed paths truncated a commit — swept it in. Git printed `warning: adding embedded git repository` and continued; the exit code was 0, and the file count in `git status --porcelain` went from 25 to 26 with nothing obviously wrong. Had it committed, a clone of the outer repo would have carried a gitlink pointing at a commit nobody can fetch. Fix: `git rm --cached .worktrees/<name>` to unstage, then add `.worktrees/` to `.gitignore` so the trap is disarmed rather than merely dodged this once. Generalization: any directory a tool CREATES inside the repo — worktrees, vendored checkouts, build caches, virtualenvs, agent scratch dirs — must be gitignored at the moment the tool starts using it, not the first time it bites, because the blast radius is a commit and the warning that precedes it is a `warning:` on stdout in the middle of a stage that prints a lot of other things. The confirming signal is cheap: after any `git add -A`, read the `git status --porcelain` list rather than its count.
