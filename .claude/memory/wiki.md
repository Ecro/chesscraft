## [wiki:architecture] declarative-content-engine | 2026-08-05
A variant-chess engine where pieces, rule cards, skill cards and special squares are all data in one shared `trigger / condition / action` vocabulary (ADR-001), with no code escape hatch. Resolution is a total order over (lifecycle event x owner layer): events E1 `generate_moves` .. E7 `end_of_ply`, and within each event the layers board square -> piece passive -> rule card -> skill card (ADR-002). Two rules the implementation forced and that are load-bearing: each square's `on_enter` fires at most once per ply, and a teleport never returns a piece to a square it already occupied this ply — without them two squares that throw pieces at each other bounce one until the depth cap, and *parity* decides where it lands rather than the content. Royalty is a content flag (`pieceDef.royal`), so no engine source names a specific piece; a royal capture short-circuits at E3 (ADR-012). Every consumer draws from its own keyed PRNG substream `rngFor(seed, ...domain)` (ADR-014), so the self-play agent's draws cannot perturb draft offers. Undo lives outside `legalActions` (ADR-013), which is what keeps the 60-ply termination bound true. The UI names no piece, card or square type — it renders from `legalActions` + the content set + the i18n bundle — which is the property that lets the schema be extended beside the UI rather than after it.
## [wiki:convention] schema-v2-content-vocabulary | 2026-08-05
Enumerate the whole content set on paper BEFORE judging whether the vocabulary is adequate — writing all 28 cards down as one line of intended effect each, with a column for what each needs, showed only 6 were expressible. Nothing short of enumeration finds that: every individual card looks authorable until you try to say it. Two schema versions followed, and both were driven by named cards rather than by taste. v2 (Phase 6a): `forEach`, a quantifier binding each matching board piece as an ownerless effect's owner and subject, without which a rule card had no square and every piece-relative target resolved to nothing; `revive_piece` over a graveyard in `GameState.captured`; `own_back_rank` resolving to the owning piece's home rank rather than the mover's; real check detection behind `check_count_at_least`, where a royal on a `block_capture`-protected square is NOT in check. v3 (Phase 6b): `swap_pieces` (two teleports cannot express a swap — neither destination is empty); an `offset` destination whose `forward` flag mirrors by the moved piece's own side; an optional `duration` on `grant_movement` / `forbid_movement` / `block_capture`, persisted in `GameState.grants` with an expiry ply, without which those three were consumed at move generation and any skill card carrying one was a silent no-op; and `piece_count_at_most`. Conventions worth keeping: a card that can resolve to nothing is not offered in `legalActions` at all; the check counter is base engine state rather than any card's, so a second card about checks needs no second counter; and durable grants are keyed by square, matching `frozenUntil`, so a granted piece that walks away leaves the grant behind. One gap was refused on purpose — an adjacency constraint wanted by exactly one card — because a `schema_version` bump plus ADR-006's editor round-trip obligation costs more than re-specifying the card.
## [wiki:architecture] table-driven-content-editor | 2026-08-05
The content editor is generated from one table, not written button by button. `src/editor/vocabulary.ts` derives the vocabulary from the Zod schemas (unwrapping `z.lazy` for the recursive condition union); `src/editor/controls.ts` pairs each entry with a `testid`, the `hosts` whose schema admits it, and a `make(ctx, current)` that produces the value a click inserts; `src/ui/Edit.tsx` `.map`s its palettes straight off that table. The consequence that matters: a vocabulary entry cannot ship without an editor control by omission, because there is no per-button source to forget to add — the only way to lose one is to delete it from the table, which the ADR-006 coverage test fails on immediately. A control the current content kind does not admit renders DISABLED rather than absent: a missing button and an unusable button are indistinguishable to the target age group, and absence is how a vocabulary quietly shrinks. Saving runs the WHOLE document through `loadContentSet` — the same fail-closed validator the game loads with (AC-011) — so a save cannot produce content the engine later chokes on, and a cross-reference an edit broke is caught at save rather than mid-match; `openDraft` is its inverse and always returns a clone. Two structural choices in the draft model exist for testability as much as UX: a fresh effect carries NO trigger (an effect that has not been told when it fires is unfinished, and seeding one makes the trigger control untestable on a single-trigger host), while a blank piece DOES carry one visible starter movement pattern, declared in `blankDraft` and pinned by its own test because the movement coverage rows index past it. Storage takes `Storage` as a parameter rather than reading `localStorage` at module load, which is what makes the quota-exceeded path reachable in tests and stops a browser that denies storage from taking the app down at import.
## [wiki:architecture] verification-harness | 2026-08-05
`npm run verify` is the project's single acceptance gate — typecheck, build, 238 vitest tests, 28 Playwright tests — and the statistical half of it is worth knowing the shape of. `src/engine/agent.ts` is a uniform-random legal-action agent that exists only as a test fixture: it calls `legalActions` and picks, sharing no code with move generation or evaluation, so the match lengths it produces are a property of the CONTENT rather than of an evaluator that agrees with the engine it measures. It is stateless — the substream is keyed by `(seed, ply, drafts resolved, side)` via `rngFor` rather than carried — which is what lets two independent replays of a seed be compared, and it draws from its own domain (ADR-014) so agent draws cannot perturb the draft offers it plays against. `playOut` budgets `PLY_CAP + 4` ACTIONS, not plies, because a draft pick is an action that does not advance the ply count; bounding by plies abandons a cap-reaching match four actions early and reports it unfinished. The suite it feeds: full-match replay determinism (AC-004), an invariant walk over random play (AC-013 — "no result implies at least one legal action" is the load-bearing one and the only thing that catches a deadlock), 1000-seed self-play with a per-rule-card length table (AC-012), and offer-independence at the SECOND draft rather than the opening, which is where a position-dependent implementation could actually be biased. The per-rule-card table is not decoration: when the median missed, it named the two cards to change. Measured on the SHIPPED bundle, never on a fixture — a median about content no player receives answers a question nobody asked. `tests/structure/no-content-in-engine.test.ts` scans `src/engine` and `src/ui` for every bundled content id, including in comments, which is why engine prose describes content generically.
## [wiki:architecture] ui-productization-baseline | 2026-08-06
The app opens on a home screen (`src/ui/Home.tsx`), and a match runs inside `src/ui/MatchHost.tsx` — the file that used to be `Play.tsx`. Two defects that made the product's own premise unreachable were closed here and are worth knowing about because their SHAPE recurs: `App` rendered the board without passing a seed, so `Play`'s `seed = 1` default applied to every match anyone would ever play — AC-004's determinism held perfectly and was simultaneously the only behaviour observable, one rule card and one pair of drafts forever; and a finished match was a dead screen, because there was no route a match could end back into. The seed now enters through an injected provider (`newSeed`, ADR-024) rather than a `Math.random()` in the component body, which is what keeps the determinism suite able to pin it through the same path a player takes, and it is shown on screen with a copy control so one player can hand another the exact match they just played. Three things are load-bearing for anyone editing this area. Second, discarding a match is guarded: `새 판`, `처음으로` and the top-level play tab all destroy a running match, and `App` — not `MatchHost` — owns the unmount, so `MatchHost` reports progress upward and the confirm lives in both places. Progress is measured as `match.states.length > 1`, NOT `plyCount > 0`, because a draft pick does not advance the ply counter and a match where both players have already chosen their skill cards would otherwise report nothing-to-lose. Third, and the part that will keep costing time: a UI restructure is one unit of work with the whole e2e suite. Phase 2 changed seven spec files, and a single helper in `editor.spec.ts` that walked `tab-play` to the board took thirteen tests down when a home screen appeared in between. `e2e/content.ts` is the shared bootstrap and now passes through `start-match`; any future phase that moves a route must budget for it up front rather than discover it.
## [wiki:architecture] ui-design-tokens-and-chrome-i18n | 2026-08-06
Colour in the UI lives in `src/ui/tokens.css` and nowhere else, and the rule that makes that true is negative rather than aspirational: `tests/ui/tokens.test.ts` scans every stylesheet EXCEPT the token file for `#rrggbb` / `rgb()` / `hsl()` and fails on a hit, so a component cannot express a colour on its own even by accident. Once that holds, dark mode and any later re-skin are data changes — which is why ADR-021 chose custom properties over a component library for an app whose entire stylesheet is smaller than most libraries' reset. Theming resolves in three layers and the ORDER is load-bearing: `:root` (light) → `@media (prefers-color-scheme: dark)` → `:root[data-theme='light'|'dark']`. Both explicit overrides must exist, not just the dark one: honouring only `data-theme="dark"` leaves a user on a dark OS unable to choose light, and that half-implementation is what the test asserts against in both directions. Specificity does the work rather than source order — the attribute selector (0,1,1,0) outranks the bare `:root` inside the media query (0,0,1,0) — so the layers can be authored in any order and still resolve correctly. As of Phase 1 the third layer is CSS-only scaffolding: nothing sets `data-theme`, so a real user reaches only the OS-preference layer until a control lands. The UI chrome's own words moved into `src/i18n/ko.ts` under a `ui.*` namespace at the same time, so the app's text and the content's text now share one file a translator can own; `tests/ui/chrome-i18n.test.tsx` enforces it with a Hangul scan plus a JSX-text-node scan, and the second one is scoped to the files the current phase owns because `Edit.tsx`'s labels belong to a later phase. That test has a known blind spot worth knowing before trusting it: it reads SOURCE text nodes, so an English string that arrives as the runtime value of an expression — `{state.result.reason}`, `{id}`, `{side}` — is invisible to it, and those are exactly what the next phase localises.

## [wiki:architecture] board-glyph-rendering | 2026-08-06
The board draws a piece as a glyph resolved from content, and every part of that sentence is load-bearing. `pieceDef.iconKey` is an optional i18n key (schema v4, ADR-017), so the glyph comes through the same `translate` indirection as every other player-facing string and the UI still names no piece — a locale that prefers a different symbol set overrides it without touching content, and a piece authored in the editor can carry one. The ABSENT case is the common case rather than an edge: `slice.ts` declares schema version 1 and `gate6a.ts` declares 2, and until the editor grows the control every authored piece lacks an icon too, so `pieceGlyph` falls back to the first grapheme of the translated name and — because `translate` returns the KEY when it cannot resolve — to `?` when even the name is missing, never to a blank square and never to the first letter of `piece.foo.name`. `iconKey` is walked by `textKeysOf`, so an unresolved icon fails the AC-016 coverage check instead of painting a dotted key across a square. Two constraints on anything that touches this area. First, the version bump is not cosmetic: `src/editor/io.ts` refuses any document declaring a version above `SCHEMA_VERSION`, so raising the constant is what lets a v4 export be re-imported — a schema change that edits only `schema.ts` ships an app that cannot read its own files. Second, the board's checker (`data-parity` plus `--color-board-dark`) and the pieces standing on it trade contrast on one axis: measured, a dark square at #b8ab90 gives a 1.97:1 checker but drops the blue/red glyphs to ~2.9:1, while the shipped #c9bfa8 gives 1.59:1 with every piece at or above 3.5:1. Decoupling them needs an outlined glyph, which is open work — do not "improve" one of the two numbers without recomputing the other.
## [wiki:architecture] game-feel-and-input | 2026-08-06
Game feel lives in `src/ui/MatchHost.tsx`, `src/ui/sound.ts` and `src/ui/settings.ts`, and four of its choices are load-bearing rather than stylistic. The animation and the last-move highlight are driven by the APPLIED ACTION, kept in component state, because the engine gives pieces no instance identity — the board is a map keyed by square, so a tween derived from diffing two board maps animates squares and a piece fades out and in instead of sliding. The action is cleared on undo and on a new match; a board that keeps highlighting a move that was taken back is lying about the past. Input is POINTER events, never HTML5 drag-and-drop: the first implementation used `draggable`/dragstart/drop, which iOS Safari does not dispatch for a touch gesture, so the gesture was dead on the only platform this product targets — and the e2e passed anyway, because Playwright's `dragTo` synthesises mouse events. Any future drag work must be driven in tests with `mouse.down/move/up`, which raise the same pointer events a finger does. The last-move highlight is an inset `box-shadow`, NOT a `background`: `.square[data-square-type]:not([data-square-type=''])` outranks `.square[data-last]` on specificity, so a background lost exactly when a piece landed on a portal or a shrine — a cue that must survive alongside other square states has to compose with them rather than compete for the same property. Sound is a pure table plus a pure decision (`synthFor`, `eventFor`) with the only impure part behind an injected `AudioBackend`, which is what lets a test assert SILENCE when muted rather than assert that a flag was read; `eventFor` is exported precisely so both endings can be checked without playing a match out, after a version that collapsed win and draw into one truthy `result` shipped a drawn match sounding like a victory. Motion goes through `--motion-*-duration` tokens so `prefers-reduced-motion` is one redefinition, set to `0.01ms` rather than `0s` because some engines treat a zero duration as "no animation" and leave the `from` keyframe applied; the Playwright suite runs reduced by default with `e2e/motion.spec.ts` opting back in, and that exception is the whole point — without it the setting would stabilise 45 specs while guaranteeing the animation path is never executed.

## [wiki:architecture] preset-is-the-room | 2026-08-06
A `preset` IS the product's "room", and knowing that changes what the editor is for. `presetDef` (src/content/schema.ts) is `{ id, nameKey, boardId, pieceIds[], ruleCardIds[], skillCardIds[] }` — a board, which pieces are in play, and the pools the rule card and the skill drafts are drawn from. That is exactly the unit the product is supposed to be about: something a child assembles, keeps, and plays with friends, with many of them accumulating over time. The decision (2026-08-06, with the user) is that **preset stays the room and content stays shared**: pieces, square types, rule cards and skill cards live in one common library that every room references by id, and a room is a selection over that library rather than a private copy of it. The trade accepted is explicit — editing a card changes it in every room that references it, and there is no such thing as a room-private piece — bought in exchange for the far smaller authoring burden and for leaving the schema, the editor's storage and the export format alone. Three things do NOT exist yet and their absence is what makes the concept invisible in the product rather than merely unnamed: the editor presents preset as one of six flat record kinds instead of as the thing you assemble, there is no room list or gallery anywhere (Home has a three-item `<select>` labelled 놀이 고르기, which reads as "choose a different game" and is the single most misleading string in the app), and sharing is whole-content-set export/import (AC-015) so a room cannot be handed to a friend without overwriting everything they made. The seed a match displays is NOT a substitute: it reproduces a deal within a room, not the room. Anyone planning the editor should treat "make, keep, name and share a room" as the axis — PLAN Phases 9 and 10 were originally written as "make the editor pleasant to browse", which touches the same files and produces a different screen.
## [wiki:architecture] pwa-service-worker-and-updates | 2026-08-06
The PWA is hand-built and has three moving parts that must stay in step. `vite-plugin-sw.ts` runs at `generateBundle` (build only — a worker holding a stale cache in front of the dev server is a debugging trap) and emits `dist/sw.js` with the build's own hashed filenames baked into a `PRECACHE` array plus a `CACHE` name derived from a hash of that array, so a new build writes to a new cache and `activate` can delete every other one. Two things about that list are easy to get wrong: `public/` is copied OUTSIDE the Rollup bundle, so `Object.keys(bundle)` never contains an icon and every asset under `public/` has to be listed by hand (the maskable icon was declared in the manifest and missing from the precache on the first pass); and `cache.addAll` is atomic, so one 404 in that list silently means nothing is cached at all. Inside the worker, every cache WRITE must be inside `event.waitUntil` — `respondWith` extends the worker's life only until the response settles, so a floating `caches.open().then(put)` can be cut off when the browser suspends the worker, and the visible result is a shell that never refreshes. Reads match by URL STRING, not by the Request object: a reload marks the requests it starts with cache mode `reload`, and matching such a Request misses, which presented as an offline reload serving the shell while both assets failed — a precache that had in fact run perfectly. Update detection lives in `src/ui/sw-update.ts` as a pure `isUpdateWaiting(workerState, hasController)` precisely because the e2e cannot cheaply drive the real state machine and a loosely-faked one rewards the wrong implementation; `hasController` is the load-bearing half, since a FIRST install also reaches `installed` and prompting there greets every new visitor with "a new version is ready". The worker never calls `skipWaiting` on its own — only in response to a `SKIP_WAITING` message the update button sends — and `applyUpdate` reloads only after `controllerchange`, with the listener attached BEFORE the message because that event can fire synchronously. Testing needs its own runner: `playwright.pwa.config.ts` serves a real build through `vite preview` on 4173, because none of this is exercisable against the dev server, and `npm run verify` chains it (a suite the authoritative gate never runs is worse than no suite). Two gaps are known and recorded rather than hidden: the e2e is Chromium-only so iOS installability — where `apple-mobile-web-app-capable` matters below 16.4 — is a manual check, and the brand hexes now live in four artifacts of which only `tokens.css` is covered by ADR-021's scan.
## [wiki:architecture] content-strings-overlay-and-rename | 2026-08-06
Authored text lives in a document-level `strings` overlay (ADR-020, schema v6), and three decisions around it are load-bearing rather than stylistic. Content records still carry i18n KEYS only, so AC-016's literal ban is intact on both sides; the overlay is keyed by those same dotted keys, one map per locale, validated in `src/content/schema.ts` as `z.record(localeCode, z.record(i18nKey, z.string().min(1)))` — the key schema is `i18nKey` rather than any string because a free-text key would mean the editor derived nothing and wrote literals at both ends, and the `.min(1)` is there because an empty name renders as an empty square, which reads as a rendering bug rather than as content nobody has named. `ContentSet.strings` is REQUIRED and defaults to `{}` while `ContentSource.strings` is optional, because every consumer would otherwise write the same `?? {}` and the one that forgot would silently take the bundle-only path for authored content. Resolution is overlay -> bundle -> the key itself, and the bare `translate(key)` export is GONE on purpose: a call site resolving without the active document's overlay renders shipped text over the author's with nothing on screen to say which one you are looking at, so `makeTranslate(strings?)` binds it up front and `TranslateContext` / `useTranslate()` deliver it inside React — which turned "a missed call site" from a silent wrong render into a compile error, and the compiler then found all eleven. `App` builds the resolver from `source.strings`, NOT from `loaded.set.strings`, because a document that fails to load still carries the text its author typed and the notice explaining the failure sits on the same screen. `missingKeys` reads the set's own overlay for the same reason: a set whose text lives entirely in `strings` is fully translated, and reporting those keys as missing would fire AC-016's own check on exactly the content this exists to make possible. The rename half lives in `commitDraft(base, kind, draft, openedId?)` and in `src/editor/strings.ts`: `openedId` ALONE decides which record is replaced — never a fallback to the draft's own id, which allowed a stale buffer to overwrite an unrelated record — and `rekeyStrings` moves the text with it, using the DOT as the boundary so `piece.rabbit` does not also rename `piece.rabbitfoot`. Keys are derived as `${id}.${field}`, which is not a new scheme but the one the shipped `ko` bundle already uses, and that is what lets one lookup serve both an authored record and a bundled one — and lets an overlay entry override a shipped record's text rather than living in a parallel namespace. `importContent` rebuilds its result from a hard-coded collection whitelist, so `strings` had to be added there by hand; a field omitted from that list round-trips as `undefined` while every schema test stays green.
## [wiki:architecture] editor-rooms-shell-and-form-guards | 2026-08-06
The editor is a two-tab shell over a room list and a library, and the decisions in it are load-bearing rather than stylistic. `Edit.tsx` holds only tab state, the shared `editor-errors` channel, `editor-storage-status` and the export/import transfer controls; the room list (`EditorRooms` -> `RoomDetail`) is the front door and the old six-record-kind surface is the library behind it (`EditorLibrary` -> `RecordForm`, the Phase 5 form body MOVED, not rewritten — the ADR-006 vocabulary-coverage gate passing UNCHANGED is the proof, and it is why the gate's `editor-draft-json` node still exists, `hidden`). **Both panels stay mounted with the inactive one `hidden`**, which is what lets a half-built room survive a trip to the library AND lets that gate keep driving `editor-kind` / `editor-save` by test id while a child never meets either until they open the tab; `styles.css` carries `.editor [hidden] { display: none !important }` so no later layout rule can defeat it. **Every remount of the library form goes through one gate**, `openInLibrary`, which confirms before discarding unsaved work — the kind picker, a record in the list, the new-record button and a room's "+ new" shortcut all remount `RecordForm` via its `key`, and a guard on any subset leaves the others silently destroying the buffer. Its dirty signal is two-way (`onDirtyChange`), because a latch that only rises prompts after every successful save; it also takes an explicit `force`, used only where the buffer's subject is being deleted — and note that clearing the dirty flag first and calling in normally does NOT work, because React has not re-rendered and the closure still reads the old value.

**The governing rule, learned across two review rounds, is about state that outlives its subject.** Both panels stay mounted deliberately, so both can be showing something the document no longer contains — after an import, after the other panel saved, after a delete. The answer has two halves and both are needed. **Save half:** each form snapshots `{record, name, text}` for its opened id at mount and REFUSES the save when the document's current version differs; the snapshot covers the overlay because an import that changes only a NAME leaves the record byte-identical. Refusing rather than remounting is deliberate — remounting discards a half-typed edit, trading one silent loss for another. **Display half:** `subjectDeleted` / `roomDeleted` are derived every render (`openDraft(source, kind, openedId) === null`); the screen says so at that moment, disables its save, and — in `RoomDetail` — still renders a row for any id its DRAFT holds that the source no longer has, strictly so it can be unticked, because otherwise the room is unsaveable with no control that can fix it. A delete of the record the form holds closes that form BEFORE the commit and without asking. Refusals store the SUBJECT, not the sentence, and re-derive each render, so one that has stopped being true disappears on its own.

**Authored text**: written only for a field the author actually TYPED IN (a non-empty field is not an instruction — editing the raw key under 고급 설정 leaves the old key's text in the box, and writing it would clobber the destination globally); the record's own key is used when it has one and `<id>.<field>` derived only when blank, so renaming a bundled record overrides the shipped key rather than shadowing it; clearing a field DROPS the overlay entry, which restores the bundled text for a shipped record and is REFUSED for one the author invented, since there is nothing underneath and the dotted key would paint across the board. **Deletion** (`deleteRecord`) is three gates in series — the last room is refused (no schema backstop: `presets` carries no array minimum), a referenced record is refused with the referring room IDS returned so the UI can name them, and the result is revalidated through `loadContentSet`. The third is not redundant with the second: `references.ts` walks only boards a room plays on, while the loader checks every board's `placements`. Overlay text is dropped by REACHABILITY — the keys the deleted record pointed at, minus any a surviving record still points at — never by the `<id>.` prefix, which strands the real entries and removes keys other records own. `references.ts` answers "which rooms use this record" for both the library's unused badge and the delete guard, over the UNVALIDATED `ContentSource` so a dangling `boardId` mid-edit returns nothing instead of throwing; it reads the COMMITTED document, which is why an unsaved room draft needs the vanished-row escape hatch above. Ids are machinery the child never invents: a new room takes the first free `preset.room-N` and the typed Korean name lives in the `strings` overlay.
## [wiki:architecture] content-addressed-art-axis | 2026-08-06
Raster art reaches the board through a SECOND content axis, not through the glyph one, and every part of that is load-bearing. `artKey` (schema v7) sits beside `iconKey` on the same four record types rather than widening it, because `iconKey` resolves through the locale bundle to TEXT and a picture is neither text nor locale-varying — sharing one slot would mean a record could carry art OR a glyph, never a glyph BEHIND its art, which is the fallback the renderer needs. `resolveMark` (`src/ui/art/resolve.ts`) is that fallback: art, else glyph, else a monogram of the translated name, else `?`; and THREE degenerate art cases fall through to the glyph rather than failing loudly — an unregistered id, an entry whose shape mismatches the caller (a `neutral` entry read for a sided piece, or the reverse), and an entry carrying an empty url. All three are reachable from an imported document, and any of them rendered as an `<img>` puts a broken image on a child's board. The registry is INJECTED into `resolveMark` for the same reason `browserStorage` and `AudioBackend` are — a test reaching into the real catalogue could only assert what the shipped art happens to be, and the unknown-id branch would be untestable by construction. Four constraints bind anything that touches this. First, art ids name the PICTURE and never echo a content id: `tests/structure/no-content-in-engine.test.ts` substring-scans all of `src/ui` for bundled content ids, comments included, so the mirrored `art.<kind>.<slug>` form fails the build and so does a comment that spells the bad id out to explain the rule. Second, assets are imported by `registry.ts`, never placed in `public/` — `public/` is copied around Rollup so the generated service worker never precaches it, and the failure was reproduced deliberately: a `public/`-style path string type-checks, builds, and renders correctly in dev while the installed offline app shows nothing. `tests/build/precache.test.ts` asserts over the BUILT `dist/sw.js` for exactly that reason, and lives outside the default vitest include because a fresh checkout has no `dist/`. Third, sides are two assets, not a CSS tint (ADR-007): the two armies currently separate by hue AND weight AND lightness as a colour-blind safeguard, and a raster inherits none of those tokens, so the separation has to be drawn in and is gated by `e2e/art-contrast.spec.ts`. Fourth, the filename prefix (`piece-` / `square-` / `card-`) is contract, not convention — it is how that gate knows which surfaces the asset can land on, and an unclassified name is a hard failure rather than a skip.
## [wiki:architecture] responsive-shell-breakpoints | 2026-08-06
The shell has three layout regimes, and which one you get is decided by TWO dimensions, never one. Portrait phone is the base: `main` capped at 480px, `.play` a single flex column. Landscape phone is `(orientation: landscape) and (max-height: 560px)`: two columns, board sticky in the first, everything else scrolling in the second. Desktop is `(min-width: 900px) and (min-height: 600px)`: the same two-column shape, but `main` opens to `min(1180px, 100%)` and the board grows to `min(100%, calc(100vh - 170px), 620px)`. The height terms are not decoration. A 915x412 landscape phone — a viewport `e2e/layout.spec.ts` pins — matches `min-width: 900px` too, so without `min-height: 600px` both blocks apply, the later one wins on source order, and the suite's own subject is silently retuned by a rule written for a different device. Whenever a fourth regime is added, its query needs a bound on the axis that separates it from all three, not just the axis that motivated it. Two mechanisms inside these blocks are load-bearing and neither is obvious. First, `main` uses `overflow-x: clip` rather than `hidden` in both two-column blocks, because `hidden` computes a used `overflow-y: auto`, which makes `main` a scroll container, and a sticky board then positions against THAT instead of the viewport and never activates (measured once at -293px). Second, `.play` declares `grid-template-rows: repeat(20, min-content) 1fr` — the board spans every row, so when it is taller than the stack beside it (the normal desktop case) grid hands the slack to the tracks it spans and blows a ~590px hole between the rule card and the hands. `align-content: start` does NOT fix that: it distributes leftover space in the container AFTER track sizing, and this happens DURING it. A trailing flexible track does, because grid gives a spanning item's size to flexible tracks in preference to intrinsic ones. Also here: `.legend li` sets `word-break: keep-all` with `overflow-wrap: break-word` as the valve, because Korean breaks between syllables by default and a 300px column split 폭탄칸 down the middle.
## [wiki:convention] button-hierarchy-and-chrome-rank | 2026-08-06
Every control on this app answers to a three-tier hierarchy, and the tier is the point rather than the styling. Thirteen buttons had rendered as thirteen identical bordered rectangles, so nothing on any screen said which one a player wanted — that, not any single button's looks, is what read as unfinished. The tiers: `.primary` is the one thing to do next (gradient, a solid colour shelf underneath, `--font-size-lg`, weight 800); a plain button is an ordinary action; `.ghost` is a control that must stay reachable without competing — the theme switch, the settings toggle. That press is not decoration — a control that does not move under a finger is the loudest "this is a web page" signal a touch UI sends. Note what did NOT happen: `flip` and the seed were MOVED, never deleted, because ADR-018 and ADR-024 own them. The entry screen is treated as a title screen off the same system — `main[data-route='home']` is `100svh` with the wordmark and card centred together as one object, the h1 at 38px with the two sides' colours running through it via `background-clip: text`, and a 6%-opacity checker on the card. ## [wiki:architecture] overlay-focus-model | 2026-08-07
A full-screen overlay in this app must decide TWO independent things about what it covers, and the pair is what the code encodes: can it be SEEN, and can it be REACHED. z-index answers neither — it is paint order, and it changes nothing about tab order, the accessibility tree, or what a test locator matches. `MatchHost` owns one predicate, `overlayOwnsScreen = Boolean(state.result)`, and two mechanisms hang off it. **`Result`** sets `inert` on `.play-cover` (a `display: contents` wrapper around the turn bar, rule bar and play body): the final position staying readable behind the summary is the entire reason `Result` is an overlay rather than an early return, and `inert` is the one mechanism that makes a VISIBLE subtree unreachable. Where `inert` is unsupported (a WebView older than Chrome 102 / Safari 15.5) the degradation is tab-order noise only, because `clickSquare` and `clickCard` both early-return once `phase !== 'play'`. React 18's types lack `inert`, so `src/ui/inert.d.ts` augments them as `string | undefined` — NOT boolean, because React 18 serialises an unknown boolean prop as the string `"false"`, and `inert="false"` is a PRESENT attribute that makes the subtree inert exactly when it should not be. The **tools row is unmounted** rather than hidden, and the reason is not accessibility: `Result` carries its own home button, so `hidden` would still leave two `data-testid="go-home"` nodes in the document and a strict-mode locator matches both regardless of visibility. **The hand-off is a banner, not a curtain, and that reversal is the load-bearing history here.** It shipped briefly as a full-screen cover the player tapped through, which marked the moment well and cost far too much for it: it hid the position two children were mid-argument about, and put a mandatory tap between every single ply. What replaced it is `.turn-toast` — 1.6s, `pointer-events: none`, no control of its own, `role="status"` with `aria-live` so a screen reader is told what the colour change tells everyone else. Nothing waits on it and nothing is blocked, so the next player moves immediately. The rule banner is cleared on the first ply so the two never stack. **The draft sheet is deliberately in neither set**: it dims rather than owns, #43 put the tools row back within reach during a draft on purpose, and its scrim passes pointers through so a player is never trapped in one. Separately, `src/ui/Sheet.tsx` is the single implementation of a modal bottom sheet, used by the match screen's detail peek and the dex's entry detail. Before it, both declared `role="dialog" aria-modal="true"` and implemented none of it; one comment even argued the claim was honest because the scrim swallows taps, which is true and beside the point — `aria-modal` tells assistive technology that nothing outside the node is reachable, and a pointer-events rule says nothing to a keyboard. It implements the four things the attribute promises: focus moves to the SHEET (not to its close button — announcing "close" before the definition is the over-eager version), Tab is trapped with wrap at both ends and interior stops left alone, Escape closes, and focus is restored to the opener when it is still `isConnected`. `onClose` sits behind a ref so the effect can depend on `[]`: both call sites pass an inline arrow, so a `[onClose]` dependency re-ran the effect on every unrelated parent render — the rule banner's timeout was enough — tearing focus out of the sheet and back in mid-read.
## [wiki:tooling] review-grade-is-not-the-signal | 2026-08-07
At this repo's current reviewer settings the REVIEW grade carries almost no information, and the flag beside it carries all of it. `reviewers.consensus: single` enables exactly one Claude reviewer; with `second_opinion.models: [codex]` that makes a voter pool of N=2 against a consensus threshold of K=2, so a finding is tagged `consensus-passed` only when BOTH voices independently land in the same file within ±5 lines at the same severity tier. Across three rounds of the Chess Craft review that happened zero times out of eight findings — the two voices produced disjoint findings rather than overlapping ones, which is the normal outcome for two reviewers looking at a 68-file diff. Since the grade counts `consensus-passed` P0/P1 only, it was **A in the round with four live defects (two P1) and A in the round with none**. It did not move once. What did move was `human_review_needed`, set by the `unverified_severe` scan over `manual-only`/`weak-consensus` P0/P1 — true while defects were open, false when they were closed. Three consequences worth knowing before reading any REVIEW from this repo. First, **read the flag, not the letter**; an A here means "nothing was corroborated", not "nothing was found". Second, **the auto-fix loop is effectively dead at this setting**: it acts only on `consensus-passed`, so with nothing ever reaching that tag it has never applied a fix and never will — every fix in that review was applied by the operator directing a round, not by the loop. Third, **the grade gate exits before the auto-fix loop**, so a grade at or above threshold stops the stage with findings open; the flag is the only thing that surfaces them. The fix, if the grade is wanted as a signal, is `reviewers.consensus: cross-check (2/3)` with more of `reviewers.installed` moved into `reviewers.enabled` — `ux-reviewer` above all, which sat installed-but-disabled through a 68-file UI redesign while every accessibility finding came from a general reviewer or a cross-model voter that happened to look. Also worth setting: `max_review_rounds: 2` is one round short for a diff of this size, because the fix round itself creates work — two of four round-2 fixes introduced defects (a save-blocking regression and a guard that could not fail), which only a third round could catch.
## [wiki:convention] card-liveness-survey | 2026-08-07
`tests/engine/card-liveness.test.ts` is the per-record survey for the shipped card set, and its design is a reaction to four rounds of `declared-but-inert-vocabulary`: every earlier guard observed that an effect FIRED, which an inert card does perfectly well. This one observes a STATE CHANGE, differentially. A rule card is driven through a scripted position and compared against a control run of the identical script with no rule card, on both surfaces a card can act through — the resolved `GameState` and the legal move set, because a `generate_moves` card never reaches `apply` and a state-only probe would call it inert. Two structural points worth keeping. Each probe carries `intended` (what the card text promises) and `current` (what the engine does today), and asserts against `current` — so the suite is green on a broken engine deliberately, and goes red the moment any card's behaviour changes in either direction, which is the signal to move `current` to `intended` and delete the defect note. And liveness alone is the wrong property: three of the four defects found were cards that DO change state, just the wrong state, so the load-bearing probes are the ones asserting a card stays INERT where it must. ## [wiki:architecture] effect-subject-quantifier-mover | 2026-08-08
Three separate things can be "the piece this effect is about", and the engine had collapsed them, which is what made three of the shipped cards unauthorable.

**The event's subject** is what the lifecycle event is about — the piece entering at `on_enter`, the piece being taken at `on_capture`. The `entering` target resolves through it, and `piece_is` / `piece_side` / `on_square` read it.

**The quantifier's binding** (`forEach`) is the piece a quantified effect is about, carried on `BoundEffect.boundSubject`. `bindEffect` sets it, and until 2026-08-08 only `generationModifiers` read it — `runEvent` built its `EvalCtx` from the ply-global subject, so a quantified effect's condition asked about the piece that MOVED while its action targeted the bound piece. The two halves of one effect were looking at different pieces. `apply`'s card-play branch was worse: it built its `BoundEffect` by hand and never called `bindEffect` at all, so `forEach` did not exist for skill cards. Both now go through `bindEffect`, and every `EvalCtx` uses `bound.boundSubject ?? subject`.

**The ply's mover** is the piece making the move, wherever it currently stands — `EvalCtx.moverSquare`, which the `mover` target resolves through. It agrees with the subject everywhere except a capture, and that single disagreement is the whole reason the distinction exists: at `on_capture` the victim has been removed and the capturer has not been placed, so the subject square is EMPTY. While `mover` and `entering` were the same expression no card could name the capturing piece, and no content used `mover` at all — two vocabulary entries resolving identically is a reliable sign that one of them is a capability nobody implemented. `apply` now also checks that the mover survived `on_capture` before placing it, because the piece to place was read before the event ran and putting it down unconditionally undid the effect's own removal.

Related: `on_own_rank` counts from the subject's own home rank, and exists because no condition knew absolute sides — see [[bug-masks-content-built-on-it]]. The whole set is pinned by [[card-liveness-survey]].
## [wiki:architecture] web-deployment-and-desktop-layer | 2026-08-07
The app is deployed as an assets-only Cloudflare Worker and has real URLs for the first time, and the desktop layout is a separate CSS layer rather than an edit to the phone one. **Deployment**: `wrangler.jsonc` declares `assets.directory: ./dist/` with `not_found_handling: "single-page-application"` and NO `main` — that absence is load-bearing, because Cloudflare does not apply `_headers` to responses a Worker script generates, so the moment `main` appears the cache policy silently stops governing whatever that script serves while every test over the unchanged file keeps passing (`tests/structure/deploy-config.test.ts` asserts `main` is absent for exactly that reason, and is the prompt to move headers into code when the Durable Object room layer arrives). `public/_headers` is copied into `dist/` by Vite and pins hashed assets `immutable` while every shell path revalidates; its route list is DERIVED from the router in `tests/build/deploy-headers.test.ts` (`ROUTES.map(routeToPath)`), so adding a route without a headers entry fails the build tests instead of shipping uncovered. `npm run verify` runs `test:build` **last** on purpose: `playwright.pwa.config.ts` rebuilds `dist/` to serve a real build, so a `test:build` placed earlier asserts a `dist/` that a later step overwrites — and CI publishes whatever `dist/` survives the run. **Routing**: `src/ui/router.ts` holds pure `pathToRoute`/`routeToPath`/`isKnownPath`; `pathToRoute` is total because the edge serves `index.html` for every path, so unknown paths reach the app and must render something (home). `boot` has a path to WRITE (`/`) and none that READS back to it — onboarding is a state of the first visit, not a place, and a URL must not let anyone skip or replay it. The frame band's upper bound is `not (min-width: 1280px)` — the desktop band's literal complement, not a `1279.98px` epsilon, which leaves a fractional sliver matching neither band. The layout is a nav rail (the same `TabBar`, rotated by CSS) plus a screen; `play` is two columns where column 1 is `.play-body` (board plus what is physically attached to it, keeping its scroller) and column 2 is what was already a sibling (turn bar, rule card, tools) — ADR-005 wanted the hands in the rail too, but they live inside `.play-body` and CSS can flatten a wrapper, not reparent a child. ## [wiki:architecture] measured-grade-and-per-side-loadout | 2026-08-07
A record's strength is a MEASUREMENT, not a number anybody typed. `src/balance/` grades a piece or a skill card by the win-rate delta it produces over `GRADE_SEEDS` (600) seeded random self-play matches against a control arm, in percentage points — the same unit for both axes, which is what lets ADR-004's budget add them. The decision (2026-08-08, with the user) came from a hard fact: for pieces there is a published closed-form value estimate, but for skill-card EFFECTS there is none, so any action-weight table would have been a developer's opinion wearing the word "objective". `predict.ts` keeps the published jumper shape `33N + 0.69N²` only as a fitted predictor — and the first fit showed it does not order this game's pieces at all (`piece.archer` +20.1pp on N=2.67 versus `piece.queen` +8.5pp on N=16.11, because the archer captures at range without moving), so it is demoted to a hint and NO provisional grade is shown: a number from a predictor known to be wrong about the strongest piece is worse than the wait.

Three things about the rig are load-bearing. **The control must differ from the arm in exactly one thing**, which is harder than it sounds — `pickDistinct` indexes with `Math.floor(rng() * pool.length)`, so a draft pool one card longer re-indexes every draw and re-randomizes white's whole opening hand. Both arms therefore withhold the reference card AND the card under measurement from the shared pool and append exactly one of them, and both carry an explicit loadout for the measured side with the other side stripped. **Grades are never stored in the document** (ADR-007): they live in a cache keyed by a hash of the record together with everything else the delta depends on, resolved BY VALUE — the reference piece, the reference card, the room, its board, the seed count, and a `MEASUREMENT_REVISION`. Hashing ids instead leaves every grade looking current when the reference piece itself is edited. **`GRADE_SEEDS` is derived**: at 200 seeds the paired standard error is ~4.2pp, forcing bands ~9pp wide and putting a pawn and a rook in one grade; 600 brings it to ~1.0pp for cards and ~2.5pp for pieces, and `bandScaleFrom` sets band width at twice the worst standard error, rounded up to a WHOLE point because the band value is what the budget charges and `loadoutBudget` is an integer.

The content shape: schema v9 gives `preset` an optional per-side `loadout` (`{ pieceId, replaces, skillCardId }`), a `loadoutBudget`, and a `grading` baseline naming the two records the room's scale is measured against — the room declares it because a constant in app source would name a piece, which AC-009 forbids. All three are refused-when-absent-but-loadout-present (ADR-010). The duel-legal gate is SPLIT (ADR-011) because a synchronous validator cannot run twenty thousand matches: `load.ts` owns what the document decides — budget and grading declared, no `win` and no `royal` in a slot, the replaced piece non-royal and actually standing on that side, and a loadout card not also in the shared pool — while `@balance/legal.checkLoadoutGrades` owns band matching and the budget sum from the cache. The UI half is wired: `src/ui/useGrades.ts` reads the cache and starts a worker for anything unmeasured, the room's cards step has the picker and budget meter that name a refusal BEFORE the save, and the lobby disables the start button when a loadout's grades cannot be verified — an ungraded record blocks the match rather than scoring as harmless. `createGradeClient` degrades to a refusing client where `Worker` is absent, because a missing capability must not become a passing budget check. Related: [[preset-is-the-room]], [[declarative-content-engine]], [[verification-harness]].
## [wiki:architecture] ai-opponent-singleplayer | 2026-08-07
Single-player lives in `src/engine/ai/`, and four things about it are load-bearing rather than stylistic. **The literature's answer was wrong here, and the number is why.** General Game Playing prefers MCTS when the evaluation cannot be hand-tuned — which is exactly this game, since rules are authored in the editor the app ships — but that recommendation is conditional on simulator speed and this engine's is ~47 µs per node (`legalActions` ~15 µs + `apply` ~32 µs, mean branching 21.6, ~45 actions per match). A one-second budget therefore buys ~470 random playouts, about twenty per root move, which is noise; the same budget buys a full depth-4 alpha-beta search (~10,000 leaves, ~0.3 s on the trusted path). Measure the simulator before accepting an algorithm recommendation — and measure it on an **idle machine**: the first pass here read 164 µs/node because three subagents shared the CPU, which made depth 4 look marginal when it is comfortable. **The budget is nodes, never wall-clock**, because the parent SPEC's replay determinism is a contract this feature inherits: a time-budgeted search visits a different node count under load, so the same seed would stop replaying. The wall-clock valve (ADR-010) is a *failure path* layered on top — opt-in via `SearchOptions.deadline`, and when no deadline is passed the search reads no clock at all, which is what `ai-determinism.test.ts` pins by counting `Date.now` calls and asserting zero. **The search must not see the future.** Every draft offer derives from `state.seed` through `rngFor`, and `apply` draws the second draft as a side effect of ply completion, so a search expanding past turn five computes the human's unseen cards. `wouldRevealDraft` decides that from the PARENT before transitioning — deciding it from the child is too late, because the child already carries the drawn offers — and the transposition key excludes `state.seed` *and* `everOffered`, not just `offers`. Keying on the seed would diverge exploration order between two otherwise-identical positions, and under a fixed node budget a different order exhausts the budget on different nodes and produces different scores: a leak that looks nothing like one. **Difficulty needed two knobs, not one.** ADR-006 chose temperature over a ranked list on the grounds that depth-limiting produces alien play rather than weak play, and measurement overruled the "one knob" half: over 400 paired games the levels never separated by more than ~0.58, because this evaluator scores material and check and nothing else, so in many positions every candidate scores identically and a softmax over equal numbers is uniform at any temperature. `BUDGET_SHARE` (1.0 / 0.45 / 0.15) is the reserved second knob now in use, and the king-safety clamp runs at **every** level — clamping only the easiest can invert the ladder in exactly the tactically decisive positions the ladder is measured on. Two operational notes for anyone editing this area. The strength tournament (`npm run test:strength`, ~13 min, deliberately outside `npm run verify`) is the detector for three levels collapsing into one opponent under three names; **any change to `search.ts` or `difficulty.ts` invalidates it and it must be re-run** — the transposition-key widening and the clamp-scan cap both did. And the AI's turn is driven from `MatchHost`'s existing `push`, with the acting side read as `pendingDraftSide(state) ?? state.sideToMove`: a draft pick advances neither `plyCount` nor `sideToMove`, so keying the effect on `sideToMove` alone leaves the computer never making its own picks and the match simply stops.
## [wiki:architecture] shipped-grades-and-hash-keys | 2026-08-07
A grade for a record that ships with the app is a CONSTANT, and re-deriving it per install is pure waste — 24,000 self-play matches to rediscover what the build machine already knew, with the picker showing a measuring state for the better part of a minute on the one screen where a player most wants an answer. `src/balance/shipped-grades.ts` holds those constants, keyed by exactly the hash `keyForRecord` computes, layered UNDER the device's own cache by `withShippedGrades`: reads fall through to the table, writes never reach it, because a shipped value is a starting point rather than something a running app revises.

The reason this is allowed to exist, and the reason it is not a return to `cost`, is the test beside it. `cost` was a number in the content that nothing verified, and it sat unread for eight schema versions. `tests/balance/shipped-grades.test.ts` re-measures every entry with the same rig that produced it and fails on any drift, refuses an entry filed under another record's key, requires the table to COVER every record the room can offer (a gap is not a broken build but it is the slow first visit the table exists to remove), and pins that editing a piece — or the room, or its board, or a reference record — yields a key the table does not contain, so a stale value can never be served as current. Self-invalidation is a property of the key, not a policy anybody has to remember.

Two consequences worth knowing. First, the measurement scope needed no narrowing after all: with the bundled records as cache HITS, opening a room queues a job only for what the author actually made, and a test counts the measurement calls to keep that true rather than assuming it. Second, the grade now appears where the record is MADE — `src/ui/RecordGrade.tsx` puts a badge on the record form for pieces and skill cards only, since a rule card is not something a side brings of its own and an empty badge would imply a measurement that never runs. The room it measures against is the first preset that declares `grading`, found rather than named, because no file outside the content set may name a preset any more than it may name a piece (AC-009). Regenerating the table means running the balance suite and copying what it reports; a delta is never hand-edited. Related: [[measured-grade-and-per-side-loadout]].
## [wiki:architecture] declared-cost-not-measured-grade | 2026-08-08
A record's price is computed from its DECLARATION — `src/balance/cost.ts` reads how far a piece moves, how far it takes, and for an ability how broad its condition and target are — and every price is a positive integer, so a budget can add it up. Grades come out queen 8, rook 4, archer 3, knight 2, pawn 1, cards 1 to 2, via `gradeOf(cost) = ceil(cost / 15)`. Two constants are calibrated rather than chosen: cards divide by 8 because measured play put the piece-to-card gap at about that (a piece swings the win rate 5-25 points, the strongest bundled card under 3, and without the divisor `skill.sacrifice` priced above the queen), and 15 raw points per grade is what puts the shipped pieces on a range a child can read.

This REPLACED a measured win-rate delta, and the replacement deleted more than it added. The measured grade could not be a price: it produced zeros and negatives so a budget could not sum it, it cost hundreds of self-play matches per record, and it ranked the archer above the queen two to one under random play. Everything that existed to make that number feel instant went with it — the Web Worker, the content-hash cache, the shipped grade table, the fitted predictor and its leave-one-out gate, and the band scale that absorbed measurement noise. Six modules and four suites. Schema v10 also removed `preset.grading`, which named the records a measurement was taken against: with no measurement there is nothing to name, and leaving the field would have been a declaration nothing reads.

The measurement rig is KEPT and changed job — it audits the ORDER the price produces instead of producing the number (`tests/balance/cost.test.ts`). Its agent is `src/balance/grading-agent.ts`, which is deliberately NOT the production AI: `ai/evaluate.ts` scores positions with `pieceValue = vectors × distance`, so grading with it would have confirmed a structural model with a structural evaluator and called the agreement evidence. The grading agent evaluates a leaf by the piece count `materialResult` already decides capped matches with, adds one ply of lookahead so free material is taken and hung material is not offered, and examines only replies that can capture — searching every reply cost 1.9s per match against 1.9ms for random play. Where price and play disagree the test records it: play rates the archer near the queen, structure cannot (four attacked squares against forty), and structure is what the price uses. Related: [[measured-grade-and-per-side-loadout]], [[shipped-grades-and-hash-keys]].
## [wiki:architecture] piece-maker-split-axes | 2026-08-08
The piece maker asks two questions instead of one, because its 7x7 grid was not a picture of anything. With the old `travel: 'slide'` picker a single lit cell compiled to a `MovePattern` with no `maxDistance`, and `engine.ts`'s `reachFrom` expands that to the board edge — so a lit cell did not denote a reachable square, a rook and a king rendered identically, and painting three cells in a line was three taps that changed nothing. Sliding therefore moved OUT of the grid into eight direction toggles with one shared reach cap (`1 | 2 | 'edge'`), and the grid now holds only bounded leap destinations and always compiles to `kind: 'step'`. Both controls carry the same `None -> Move -> Capture -> Both` cycle, so `movement` and `attack` each hold at most two patterns — one slide, one leap — and the `attack`-omission check compares them PER KIND BUCKET, never by array position, because an index comparison mis-detects equality exactly on the multi-pattern pieces the split exists to unlock. No schema change was needed: `movement` was always `z.array(movePattern).min(1)`. `kind: 'jump'` is accepted into the grid and re-emitted as `'step'` — `reachFrom` branches on `'slide'` only, so the two are provably indistinguishable in play, which also means an open-and-save is a de facto per-record migration rather than the deferred type-level removal. What the reader no longer refuses is the interesting case: a piece that both slides and leaps, and the bundled archer whose movement and attack use different kinds. Three things sit on top of it and each pays for itself twice. The preview (`PiecePreview.tsx`) splices the draft into a scratch 7x7 document and asks the ENGINE via `legalActions` — never its own arithmetic, which would drift from `reachFrom` and would make the parity test circular; its probe id is DERIVED per document (`probeIdFor`), because a fixed one silently collides with an imported record and kills the preview for that whole document forever. Live validation runs `commitDraft`/`loadContentSet` — the same validator the save button runs, reached through the same extracted `prepared()` pipeline, so "the same problem, earlier" is true by construction rather than by a lookalike check. And the makers open on a gallery: a new piece starts from one the document already has, a new card from a filled-in template built through `writeRecipe` itself, and a remix derives its OWN `nameKey`/`textKey` so renaming the copy cannot rename the original. Tabs are limited to piece / ruleCard / skillCard — a special square's whole content IS its effects, and a board or a room has no simple maker, so splitting their screen would hide the only form there is behind a second tab.
## [wiki:architecture] turn-is-card-then-move | 2026-08-08
A turn is `[play_card?] → move`, and the whole turn is ONE ply. The card resolves without handing the board over and without advancing `plyCount`; the move that follows does both. `GameState.turnCard` carries the card played this turn and answers the two questions that shape depends on — may I still play a card (only while it is null) and am I awaiting a move (only while it is not). It is what `legalActions`, the end-turn escape hatch, the UI and the AI's position key all read, and every close-out must clear it, including the royal-capture short-circuit that enumerates its own overrides rather than falling through.

Three consequences are load-bearing and none of them is obvious from the rule. **Consumption moved to the card branch**: `bumpTurns` was the only writer of `draft.used` and took the card id from the action closing the ply, so leaving it there after the close-out moved to the move would have made every one-use card infinitely reusable — with nothing to see, because the card still resolved. **The ply close-out is SPLIT, not moved**: a `win` action and the royal transition run per ACTION (a card can destroy a king, and the follow-up move's starting board is already royal-less, so a per-ply check would find nothing lost and let the match run to the cap), while `checkCount`, the `end_of_ply` event and the `PLY_CAP` material result belong only to the turn-closing action. **Depth counts plies in the search**: a card child is neither negated (the side to move did not change, so negating reads the mover's own follow-up as the opponent's choice and prices every card at the worst thing its owner could do next) nor charged a level (charged, a card line at the frontier is judged one action deep against a move line judged a full ply deep).

Anything bounded in ACTIONS rather than plies must double: the AC-013 invariant walk, `playOut`'s budget in `agent.ts`, and that agent's RNG key, which without a `turnCard` term drew the same number for both draws of one turn. Related: [[effect-carries-its-source]], [[measured-grade-and-per-side-loadout]] (superseded by the cost model).

## [wiki:architecture] effect-carries-its-source | 2026-08-08
Every lasting effect names what created it. `frozenUntil` is `Record<square, {untilPly, sourceId, layer}>` and `ActiveGrant` carries the same two fields; `executeActions` copies them off the `BoundEffect` it already holds, so it is one line at each of the two write sites. The layer matters as much as the id — a freeze from a square and a freeze from a card are identical on the board, and which one it was decides whether a player walks away or waits it out.

`src/ui/liveEffects.ts` is the single derivation the badge, the legend chip and the peek sheet all read; deriving each separately is how a badge with no chip beside it appears, which reads as a rendering bug. Two rules inside it are not arbitrary: the badge picks by how much an effect changes what the player may do (frozen > forbidden > shielded > granted) rather than by insertion order, and the row sorts by square so it does not reshuffle under a thumb.

Only DURATIONED effects are visible, and that is a real limit rather than an oversight: a grant with no `duration` is consumed by the E1 generation sweep and never reaches `state.grants`, so a piece passive's permanent grant has no state to render. Recorded as a Non-Goal. A one-shot flourish keys on `square:kind:sourceId:(remaining + plyCount)` — the absolute expiry, because `remaining` ticks down every ply and keying on it marks every surviving effect as newly arrived on every ply.

## [wiki:architecture] piece-info-affordances | 2026-08-08
In-match piece info arrived as TWO routes on purpose, and the shape is the load-bearing part. Every board entity except the piece already had a tap-to-explain path — skill and rule cards through the hotbar's `SlotDetail`, painted square types through the legend chips, all landing in one content-agnostic `Peek` sheet; the piece's `nameKey`/`textKey` existed but were reachable only from the dex, a different route than a live match. The floor is the hint bar's fourth state: `.hint-bar` now renders one of {rejection, armed card, selected piece, idle hint} in priority order, so no new gesture has to be discovered and a rejection still wins the slot. The accelerator is press-and-hold, which is the ONLY route to what selection cannot reach — the opponent's pieces and a turn with a card armed. **`usePressInspect` owns tap, drag AND press, not just the press**, and that is the whole design: a press timer bolted beside an untouched `onClick` is `[fail:design] rule-keyed-to-event-not-state` wearing a new hat — one finger, two commits. It also deliberately does NOT ride the drag path, because `beginDrag` refuses a square that is not the mover's own and refuses everything while a card is armed; those guards are correct for dragging and fatal for inspecting, so the hook starts its timer on every square and leaves them untouched. Three implementation facts worth carrying: (1) **`setPointerCapture` is the wrong answer here** — capture retargets later events to the captured element, so the release of a drag from a1 to b2 arrives at a1 and every drag resolves as a tap on its origin; window listeners for the sequence's lifetime give the same off-board visibility without touching event targeting, and React's delegated handler still resolves a release over a square first. (2) The click guard **names the square** whose click is spent rather than raising a boolean — a drag ends on a square that never receives a click, and a boolean left armed there swallows the next Enter/Space. (3) The hover tooltip is a **child of its square**, which is what satisfies WCAG 1.4.13's "hoverable" for free (moving onto it never leaves the element owning the hover); its Escape dismissal must be **board-wide**, because the tooltip is drawn above its square so a pointer resting on it is geometrically over the NEIGHBOUR — per-square suppression made Escape spawn the neighbour's tooltip under a motionless pointer. The move region renders exactly one of {7x7 grid, "cannot be drawn" notice} and a rendered-but-empty grid is a test failure, not a display state — `readGrid` returns null for multi-pattern/mixed-travel pieces and `piece.archer` in the shipped bundle is one, so both branches are exercised by real content. `mobile-webkit` joined the Playwright matrix for AC-008 and immediately earned its keep: it surfaced `FINDING-webkit-back-guard` (the back guard's confirm never fires; unknown-path URL normalization intermittently does not land), both out of scope and both skipped on WebKit only against that document. It carries a 90s per-test timeout while the other projects keep 30s — measured, not guessed: the suite passes at `--workers=1` and three tests time out when `verify` runs all three projects at the default worker count.

## [wiki:architecture] refusal-reasons-and-price-explainability | 2026-08-08
A refused action names its cause, and a price shows its arithmetic — two surfaces that used to answer with a shrug. `describeRejection` returns a `RejectionReason` CODE now, never prose: it used to return untranslated English that the hint bar printed verbatim, so a Korean-speaking player read "that card cannot target those squares", and the engine owning a player-facing sentence is the same mistake as the engine owning a piece's name. ## [wiki:architecture] sprite-grid-24-and-its-two-metrics | 2026-08-09
The sprite grid is 24x24 (it was 12x12), and the thing to know before touching it is that **raising a grid halves the physical size of every feature**. A mark renders at 34px on this board, so a 24-grid cell is 1.42 device pixels where a 12-grid cell was 2.83 — a one-cell outline is thinner than the display draws at strength AND stops being a large enough share of the ink for `e2e/art-rendered-contrast.spec.ts`'s 10th percentile to land on it. Nine board squares failed that gate while `tests/ui/art-contrast.test.ts` stayed green, because the character gate reads the table and cannot see rasterisation. So a meaningful share of the new resolution has to be spent on a thicker outline rather than on detail, and the net gain is smaller than "four times the cells" suggests. Two metrics hold that balance and they pull in opposite directions on purpose — `subBlockDetail >= 20%` (art drawn at 12 and doubled scores 0%, which is what a delegated pass produced while passing every pre-existing gate) and `outlineShare >= 35%` (set where the pre-migration sheet sat, 41-59%) — with `tintShare >= 30%` beside them so a silhouette still tells the two armies apart. They live in `scripts/sprite-metrics.ts` and are enforced by `tests/ui/art-refined-pieces.test.ts`, whose roster is DERIVED from `artRegistry` intersected with the bundled content's claimed `artKey`s; a hardcoded roster is false-green, because `toHaveLength(12)` on a literal proves only that the array is the length of itself.

**There is no sprite generator.** `scripts/gen-sprites.ts` SCORES candidates against `gates.ts`; it does not draw. All 209 tables are hand-authored (125 in `src/ui/art/pixels.ts`, 84 re-authored as candidates in `scripts/spare-sprites.ts`), and **six drawings live in both files** — `lance`, `crossbow`, `warhorse`, `watchtower`, `censer`, `cloak` — so refining one copy silently diverges the generator from the sheet, and twelve exception names exempt eighteen tables. The PLAN's "209 - 12 = 197, the pieces are disjoint from the spares" was wrong and three validator passes confirmed it, one of them after reading the header of the unclaimed-spare block without reaching the collisions further down.

Migration mechanics that are worth reusing: `scripts/upscale-sprites.ts` holds the pure `upscale(rows, k)` block expansion, the codemod that applied it, and a `--verify --baseline <sha> [--except names]` audit that re-derives every table from a pinned commit. The baseline is a **literal SHA in the PLAN frontmatter, never `HEAD`** — `HEAD` moves the moment the migration commits, at which point the check degenerates to `upscale(migrated) == migrated` and reports a total failure for a correct migration. The audit reconciles `found == checked + skipped` itself and errors on an `--except` entry matching nothing, so "191 checked" cannot be confused with an under-audit. Gate constants are DERIVED from `SPRITE_SIZE`: `RECT_CAP = 5 * SPRITE_SIZE` and `SHEET_DIVISOR = (SPRITE_SIZE * 3) / 20`, written as a fraction because `0.15 * 12` is `1.7999999999999998` and not bit-identical to the `1.8` it replaces. Leaving the divisor at 1.8 does not weaken the sheet-wide compression gate at 24x24, it kills it — the upscaled dither fixture clears a floor of 1.8 and is caught only by 3.6, which is why `art-gates.test.ts` asserts BOTH polarities. `CORNER_RADIUS` is in CELL units and had to double (0.3 -> 0.6) just to hold the rendered result still; `pathOf` clamps every corner to a third of its shorter adjoining edge, so past ~0.667 the constant stops mattering and a radius sweep reads as flat. On this sheet the sweep is flat for a second reason too: the worst rendered mark is a painted square at 27px whose ratio is set by its palette tone, and rounding cannot change a fill. Related: [[spare-art-pool-and-sprite-gates]], [[chess-craft-pixel-redesign]].
## [wiki:architecture] bundled-content-stamp-and-additive-merge | 2026-08-09
A snapshot of shipped content written into user storage is a FORK, not a cache — so the app must persist the author's delta against a named bundle version, and the name is the cheapest thing that works: a flat set of ids. `strange-chess.content.v1` holds the entire `ContentSource`, and `initialSource()` returned it whenever it validated, so the first editor save froze that browser's catalogue permanently and every later release's presets, boards, pieces and cards reached only fresh installs. The fix is one line — `merged = saved + { bundle records : id ∉ stamp ∧ id ∉ saved }` — where the stamp (`strange-chess.bundle-stamp.v1`, `{ ids: string[] }`) is the set of bundled ids as of the author's last save. The stamp exists solely to disambiguate: without it, an id in the bundle and absent from the saved set is either a record the author DELETED or one that is NEW, and guessing either way is visibly wrong (a resurrected room, or content that never ships again). Four decisions carry the design and each has a failure it prevents. (1) ADDITIVE-ONLY: never refresh a bundled record already present, so an author's record cannot be overwritten by this feature — structurally impossible rather than guarded. The accepted cost is that later fixes to bundled records do not reach an install that has saved; adding that later means putting fingerprints in the stamp, an extension of this shape rather than a rewrite. (2) The stamp needs its OWN key, because the read path goes through `importContent`, which rebuilds the source field by field and silently drops any unknown top-level field on the very next read — a stamp stored as a document field survives zero round trips. (3) `initialSource()` WRITES NOTHING; the merge is recomputed every load. A load-time stamp write is self-defeating: the additions land in the stamp and not in the saved document, so the next load reads them as records the author deleted and drops them — it works once per session and reverts on reload. The stamp advances only on the editor's save path and only when `saveContent` returns ok (it REFUSES on quota rather than throwing, so an unconditional write puts the stamp ahead of content that was never stored). The invariant is one-directional and worth memorising: THE STAMP MAY LAG THE CONTENT, NEVER LEAD IT. A lagging stamp is self-healing — every affected id becomes "author created it", so the saved copy is kept and the next accepted save re-synchronises. (4) An addition can DANGLE (a new room needs a card this author deleted), and `loadContentSet` Pass 2 rejects the whole document, so the merge validates and declines additions to a fixed point; the worst fixed point is the saved document, which is valid by construction because `loadStoredContent` reaches its ok branch only through `importContent`. The progress rule matters because Pass 2 has error classes whose attribution does NOT name the record that changed (the loadout `replaces` check reports against a preset, paired-square symmetry against a board): decline every addition named by or referenced from a record in an error, and if that set is empty decline ALL remaining, so each round strictly shrinks the candidate set. Absent-case, the repo's most-recurring class: no stamp is the state of every install alive today, and the defined behaviour is to synthesise one from the CURRENT bundle, which adds nothing and resurrects nothing — those installs forgo the backlog once and every release after that is exact.
## [wiki:architecture] content-provenance-derived-not-stored | 2026-08-09
"What we shipped" and "what the child made" are distinguished WITHOUT a schema field: a record is official iff its id is in `bundledContentSource` (`src/content/provenance.ts`). The alternative — an `origin` field at a new schema version — was rejected because every saved document in existence would be in the field-absent state, which is this repo's most-recurring failure class; a derived answer has no absent case to define. Three rules make the derivation exact rather than approximate, and all three are load-bearing. **Fork-on-edit** (`src/editor/fork.ts`): editing an official record's rules produces the child's own copy under `<id>-2`, so an official id always names an unmodified official record. A RENAME must not fork, and it does not — a rename writes into `source.strings` and leaves the record byte-identical, so the structural comparison answers false with no per-kind list of fields to ignore. Two corrections were needed and both are the interesting part: the record AS STORED must also match the shipped one (an imported set carrying its own `piece.king` is the child's, not ours, and a pure rename was forking it), and the copy must take its OWN derived `nameKey`/`textKey` with the current words carried across (a copy sharing the original's key sends the next rename to the shipped record — the same answer `MakerGallery`'s remix reached earlier for the same reason). **The id field is read-only on an official record** (`isPristineOfficial`, shared by the fork and the lock so the two can never disagree), which closed a live data-loss path: typing in it re-derived the key fields and `commitDraft` replaced the record at `openedId`, destroying the shipped original. **Hiding, not deleting**: official content is tucked away under its own storage key `strange-chess.hidden.v1` (never a field on the document — `importContent` rebuilds field by field and drops unknown top-level fields on the next read), and hiding filters LISTS only, never the document, so it cannot produce an unloadable set and needs no reference gate. The one exemption is load-bearing: a picker always shows what the edited thing ALREADY selects, because `VanishedRows`/`ChipList` decide "this reference is broken" from the array they were handed, so filtering without the exemption tells a child their own piece is gone and the next save drops it. Six list surfaces apply the filter and the ordinal-bearing `recordLabels` — enumerate them from `visibleIds`' call sites rather than from memory, since the count grew from three to six across two review rounds.
## [wiki:architecture] unified-movement-and-placement-ux | 2026-08-09
Movement is ONE 7x7 grid and placement is ONE painter, and both replaced surfaces that had multiplied around a single truth. The maker had SEVEN movement surfaces in one fieldset — a leap grid, an 8-direction slide dial with a shared reach picker, a separate capture-pattern editor that was a second uncoordinated writer of `d.attack`, an engine preview, a dex sentence, two prose notes explaining leap-vs-slide, and a top summary. No document ever decided they should co-exist; each arrived by its own justified ADR and the co-presence was accretion. The collapse works because **a cell carries its ray**: a slide vector must be one of the eight compass units, so a slide IS a contiguous line of cells outward from the centre, and the only thing the grid lacked was a cell state meaning "and keeps going" — the outermost ring cell, drawn as an arrow, compiling to a slide with no `maxDistance`. That makes a cap of exactly 3 inexpressible and `piece.charger` stays read-only; AC-006 pins it as the SOLE exception by asserting the refusal SET rather than a count, so a second one is a failure instead of drift. `PieceGrid.reach` went scalar -> per-direction -> **per-direction-and-axis**, and the last step was forced rather than chosen: with one cap serving two axes, a tap on the capture grid could only overwrite the cap (silently lengthening a MOVEMENT ray on a mode the child was not looking at) or adopt it (drawing the square they DID tap as untouched while a square they never tapped became the tip). Both are edits a child cannot see, and the schema was never the constraint — `movement` and `attack` are separate arrays each carrying its own `maxDistance`, so the editor had been the narrower of the two all along. Two consequences worth knowing: `bucketize` had to stop refusing a second `slide` pattern and `writeGrid` had to acquire a canonical order (capped ascending, uncapped last) because N caps means N patterns; and the `attack`-absent promotion must copy the CAP with the direction, or a round-trip invents an `attack` for a record that had none. Round-trip equality against the shipped document is NOT achievable and never was — `writeGrid` sorts vectors while the bundle is hand-written in a human order — so the real invariants are semantic identity (same kinds, same vector SETS, same caps, `jump` normalised to `step` since the engine gives both `maxSteps = 1`) plus byte-level IDEMPOTENCE. The `.move-grid` is fluid at `max-width: 344px` with a negative `margin-inline` escaping its fieldset padding; the shipped `width: 294px` was never honoured (`max-width: 100%` clamped it) and measured 36.3px per cell against a 44px touch target — 38.9px is what is recoverable without restructuring padding three editor screens share, and an e2e asserts that floor rather than the aspiration. On the placement side `RoomDetail`'s painter was extracted to `PlacementPainter.tsx` and the board RECORD adopted it; the `testIdPrefix` prop is load-bearing rather than cosmetic because `Edit.tsx` keeps BOTH editor panels mounted with the inactive one `hidden`, so one namespace makes `getByTestId` ambiguous exactly when a test drives both surfaces to compare them.
## [wiki:gotcha] min-height-is-a-floor-not-a-guard | 2026-08-11
`min-height` on a flex child is the value a squeeze STOPS AT, not a guard against being squeezed — and in this shell that distinction is what clipped a button's text. Every screen is a column flex container (`.phone > section`), so every direct-child button carried the default `flex-shrink: 1`. When a column's content exceeds the shell height, the browser resolves the shortfall by shrinking flex items FIRST and only engages that column's own `overflow-y: auto` once shrinking is exhausted. `놀러 가기` (`button.primary.xl`, natural height 70.8px = 18+18 padding + 3+3 border + 18px x 1.6 line box) therefore bottomed out on its 44px `min-height`, leaving a 2px content box under a 28.8px line box, and `main`/`.phone`'s `overflow: hidden` cut the glyph bottoms off. The fix is `flex-shrink: 0` on the BASE `button` rule, which is the same computed result as `flex: none` — the idiom already used 39 times in this sheet, and already applied container-locally at `.result-actions`, which is the only reason the identical `primary xl` on the Result screen never clipped. Three things are worth carrying forward. **First, the reproduction is viewport-shaped and narrow**: it does not appear at 390x844, 412x915, 768x1024, 915x412 or 1280x900 — at all of those the column fits and the shrink path is never taken. It needs a screen short enough to overrun, e.g. 360x560, where the button measures 52.2px and clips with the fix reverted and 70.8px without. Any future test for a squeeze-class defect must assert that its viewport still overruns, or it silently measures nothing; `e2e/button-label-fit.spec.ts` does exactly that as its first test. **Second, `e2e/a11y.spec.ts`'s 44px floor is not a fit check and never was** — 44px IS the clipped state here, so that suite was green throughout. A target-size gate and a text-fits gate are different claims. **Third, the bevel is an inset box-shadow drawn OVER the padding area**, so inline padding below `--bevel` (3px) puts a label under it; that is why the guard's failure threshold is the bevel-clearing floor (`--space-2`, 5px) while ADR-007's 11px/5px tiers are REPAIR targets. Conflating a repair target with a failure threshold flagged six families (`.turn-right`, `.legend`, `.chip`, `.slot-options`, `.slot-detail`, `.draft-cards .card`, all at 8px) that had nothing wrong with them. A rule that draws no bevel at all (`box-shadow: none` — `.piece-strip`, `.tabbar .tab`) is exempt by derivation rather than by allowlist. The guard lives in two halves: `tests/ui/button-label-fit.test.ts` reads stylesheet TEXT (five rule shapes, button set derived from `<button className=...>` in the JSX so a new family is covered the day it is written) and cannot prove any label fits; `e2e/button-label-fit.spec.ts` measures, and reaches the match screen and the room builder explicitly because `.match-tools` and `.build-steps` render nowhere a tab click can go.

## [wiki:architecture] card-legibility-and-notice-stack | 2026-08-13
A skill card play is now announced by name, and the three surfaces that say so share one lifetime. `src/ui/cardPlays.ts` answers "was a card played between these two states, and what did it touch" as a pure function over `match.states` — never raised from a handler, because four routes reach that state (the human commit, the no-target commit button, the computer's `push`, and `undo` stepping back across one) and `[fail:design] rule-keyed-to-event-not-state` has three recorded instances of behaviour attached to the input that usually produces a state. `impacted` is the union of a live-effect key change and a board-occupancy change: a freeze writes effect state and moves nothing, a swap moves two pieces and writes none, and a derivation built on either half alone draws nothing for a third of the shipped deck. `effectKey` is exported for one reason only — the absolute-expiry rule it encodes is unobservable through `cardPlayBetween`, since a card play never advances `plyCount`, so both encodings agree on every pair that function is ever handed; the rule actually bites in `MatchHost`'s older `arrived` derivation, which diffs across moves.

`MatchHost` holds the announcement as a LATCH (`cardNotice`), not as a render of the derivation. The identity is derived; the visibility is a `useState` flag on a timer keyed to `history-length + cardId`. That split is the whole design: a purely-derived banner lives exactly as long as the player takes to act next — 200ms for a fast player, five seconds for a slow one — because `match.states` advances past the pair that shows the play. The cost of the latch is that it also outlives an UNDO, which is a real bug it caused once and now clears explicitly in `doUndo` and `startNew`, and that it must be gated on the same condition the banner is: when the card's record cannot be resolved the banner is suppressed, and `impacted` has to be suppressed with it or rings appear with no words to explain them.

Five notices now share one coordinate and are chosen by ONE ordered pick — card > rule > hand-off > ai-thinking — instead of four ad-hoc conditions each naming the others. A hand-off displaced by a card banner is QUEUED (its timer does not start until the banner clears), not dropped, because "whose turn is it" must not be lost to a card play. `ai-degraded` is deliberately OUTSIDE the pick: it is persistent and about the match rather than the ply, and it renders elsewhere, so it may coexist — written down because "not in the list" and "forgotten from the list" are indistinguishable otherwise.

Two constraints worth knowing before touching this. The impact ring is a CHILD element, not a pseudo-element: `[data-last]` owns the square's `::before` and the legal-move dot owns its `::after`, and ADR-005 deliberately leaves the human path ungated so the player picks their owed move while the ring is still running — so both pseudo-elements are genuinely contended and the ring collided with the move affordance until review caught it. And every onboarding seen-flag lives in `src/ui/onboarding.ts`'s `ONBOARDING_KEYS`, which `tests/helpers/onboarding.ts` and `playwright.config.ts` both iterate; `MatchHost` takes `storage` as a prop and shows nothing without it, which is what keeps fifteen direct-mount board tests from landing behind an undismissed sheet.
## [wiki:architecture] settlement-grants-and-board-size | 2026-08-14
Schema v12 answers one question in one place: **which square is an effect actually about, once the piece it names has finished moving?** The board is keyed by square with no piece identities, so an effect naming the MOVER has no correct square until the ply's cascades finish — at `on_capture` the capturer still stands on `action.from`, and a square-keyed write lands on the square it is about to vacate. That is why the old capture-tax card was inert for four months. The answer is a SETTLEMENT step in `transition`, sitting after E6 and before the card branch's early return — the one position both branches share. It drains `m.deferred`, and its position matters against E7 and only E7 (E7 can destroy the subject; the check tally cannot see it either way, because `settled` at `engine.ts` is built without `m.grants`). Three callers use it: `protectRelocatedAfterPlay` (v11, unchanged), `lockRelocatedAfterPlay` (v12, a `forbid_movement` grant at `untilPly = plyCount + 1` — correct because the card branch returns WITHOUT incrementing `plyCount`), and `freeze_piece` targeting `mover`, gated on an explicit `midMove` parameter passed only by `on_leave` and `on_capture`. `midMove` is a parameter and not `moverSquare != null` because that test is wrong in both directions — `cascadeEnter` passes a non-null `moverSquare` for every `on_enter`, and so does `end_turn`'s E7, after the queue has already drained.

Two things about the board model are worth knowing before touching any of it. **Grants are keyed by square and now carry `beneficiarySide`** (required, populated at three push sites): square-keying is right for a freeze, where a lingering effect is a penalty the next occupant inherits, and inverts for `block_capture`, where it handed cover to whoever walked in next. The beneficiary is read off the OCCUPANT, never the caster, so a card written to shield an enemy piece keeps working; when the target square is empty — which at `on_capture` it ALWAYS is, since the victim is removed before the event runs — it falls back to `runEvent`'s raw `subject` parameter, deliberately not `ctx.subject`, which under a `forEach` quantifier is the bound piece and can be the capturer's own. **And royals are unreachable from skill cards through FOUR guards**, not the one an ADR first inventoried: `candidatesFor` drops them from every choice slot (the outermost — a royal is never even OFFERED as a target), `executeActions`' `mayAffect` refuses their square for skill-layer effects, the card branch skips royal bound subjects, and `generationModifiers` drops skill-layer grants standing on them. Any feature that needs to reach a king must name which of the four it is carving out.

Board size is content, not engine: `inBounds` reads `state.width`/`state.height`, slide distance defaults to `max(width, height)`, and the renderer sizes its grid from state — the 8x8 room ships without one engine line. What board size DOES touch is the ply cap and the cards. `PLY_CAP` moved 60 -> 160, chosen from measured uncapped distributions rather than guessed (6x6 median 42 / p90 92; 8x8 median 87 / p90 170), because 60 was about the p72 of the SMALL board and was deciding a third of every room's matches through `materialResult`. The raise exposed a hard deadlock — a side whose last pieces were all frozen had no move, no playable card and no `end_turn`, so the match silently stopped — closed by offering the forced pass whenever the mover has neither a move nor a playable card, which does not reintroduce a voluntary pass because there is nothing to skip. Every 6x6 baseline was re-measured against the new value rather than adjusted to fit it, and the decisiveness survey changed what it RANKS (cap rate collapsed to 0-4%, so it now ranks by median plies). A size-relative cap would serve both rooms better and is the recorded alternative not taken.

## [wiki:architecture] state-only-event-derivation | 2026-08-26
Deriving "what happened" from a sequence of immutable STATES is not the same as knowing what was done, and the gap is where the defects live. `src/collection/observe.ts` folds a finished match into a collection reading only `Match.states` plus the board definition — deliberately, because ADR-008 keeps `src/engine/` out of it — and three separate review lenses each found a different way that derivation was wrong. The progression is the lesson. Version one diffed square OCCUPANTS, which reports a piece captured in place as having moved, because its square's occupant changed. Version two switched to ARRIVAL — only the piece that moved ends up somewhere it was not, a victim vanishes rather than arrives — which fixed capture but still filtered to `before.sideToMove`, so a card that relocates the OPPONENT's piece (`skill.shove`, a shipped `teleport_piece` at a `chosen_enemy`) credited nobody, and it still counted a piece that `spawn_piece`/`revive_piece` had put on the board as one that moved there. Version three attributes each arrival to the side the arrived piece belongs to, and charges arrivals against that side's POPULATION growth for that id first, so an arrival explained by a piece coming into existence is not a move. What survives even that is promotion: the engine rewrites the landed piece's id inside the same transition, so the new id's count grows (reads as a creation) and the old id's count falls (reads as a capture) and neither is credited — closed by amending the acceptance criterion (ADR-009) rather than by more inference, because the information genuinely is not in the states. The generalizable rule for this codebase: before deriving an event from two states, enumerate every engine action that can produce the same state delta — `apply` in `src/engine/engine.ts` is the list — and decide explicitly which ones your derivation conflates. Where a case cannot be separated, say so in the criterion and pin it with a test rather than leaving the derivation quietly wrong; a hand-built state pair is enough and does not need a reachable match. The three cheap discriminators, in order of strength: arrival over occupancy diff, per-side attribution over mover-side attribution, and population change over per-square change. One more shape worth knowing: a same-transition destroy-plus-create of the SAME id nets to zero population change and still reads as a move — unreachable in shipped content, reachable by a card authored in the editor.
